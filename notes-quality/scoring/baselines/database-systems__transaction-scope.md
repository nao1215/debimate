## 冒頭
Transaction Scope（トランザクションの範囲）は、`BEGIN` から `COMMIT` までの間にどの処理を入れるかの決め方です。DB（データベース）のトランザクションが巻き戻せるのは、その DB 内の更新です。外部 API の呼び出しまで取り消せるわけではありません。

レコードを更新すると、DB はそのレコードに他からの更新を待たせるロック（行ロック）を取り、通常はトランザクションが終わるまで外しません。そのため、範囲を広げるほど、DB 接続と早い段階で取った行ロックを長く保持します。

外部システムを呼ぶ処理では、DB 内の更新と外部の処理をどこで分けるかが問題になります。在庫を引き当て、決済 API を呼び、注文のレコードを作る、という 3 つの処理があるとします。どれかが失敗した時に全て取り消すつもりで、3 つを 1 つのトランザクションに入れた場合を考えます。

上の形では、決済 API の応答時間がそのままロックの保持時間に足されます。下の形ではロックが短く済む代わりに、決済の呼び出しを確定と別に管理する必要があります。

<br>

本記事では、PostgreSQL の挙動を基本に、ロックを保持している間に何が起きるのかと、外部の呼び出しをどこに出すのかを説明します。ロック待ちの実験には PostgreSQL 17.10、外部 API とロールバックの実験には SQLite を使います。範囲を広げた時の困り事から始めて、次の疑問に答えます。

- なぜトランザクションを広げると困るのか。
- 決済の応答を待つ間、DB の中のトランザクションは何をしているのか。
- 外部 API の呼び出しは、なぜロールバックで戻らないのか。
- 決済の依頼を DB に残してから呼ぶと、何が変わるのか。
- トランザクションを短くしても、どんな問題が残るのか。

複数のレコードを違う順序でロックして互いに待つ状態は Deadlock、他のトランザクションの変更がどこまで見えるかを定める分離レベルは Transaction Isolation、複数の DB にまたがる確定は 2PC（Two-Phase Commit、2 相コミット） の題材とします。

## 節の並びと最初の 1 文
- トランザクションを広げると困る理由: 行ロックを保持している間に待たされるのは、同じレコードを更新しようとしたトランザクションと、`SELECT ... FOR UPDATE` のように競合するモードのロックを取ろうとしたトランザクションです。 ［図: PostgreSQL 17.10 で測った、注文 B のロック待ち］ ［コード 2 個］
- ロールバックで戻らない外部 API の呼び出し: 外部 API をトランザクションの中で呼ぶと、待ち時間に加えて、DB を巻き戻しても外部で起きたことは戻らない、という問題が出ます。 ［コード 1 個］
- ロールバック後に残る決済の実験: 図の順序をローカルで実行するコードで確認します。 ［コード 3 個］
- 結果が分からない COMMIT: `COMMIT` がエラーを返しても、DB 側では確定していることがあります。
- 決済の依頼を DB に残してからの呼び出し: トランザクションを DB の更新だけに絞り、決済の呼び出しを確定の後に置くと、行ロックと DB 接続の保持時間は DB 内の処理で決まります。 ［コード 1 個］

- 欠点: 範囲を狭めると、トランザクションの外に出した処理を状態と再送で扱います。
- トランザクションを短くしても残るケース: 複数のレコードのロック順序が逆になる問題は、トランザクションの範囲を狭めても消えません。

## 結び（利点以降）
### 利点

- 行ロックの保持時間が DB の中の処理で決まり、相手のシステムの遅延に左右されなくなる
- 応答待ちで DB 接続を握らないので、同時に捌ける件数が接続の本数で頭打ちになりにくい
- 巻き戻す対象が DB の中だけになり、外部の副作用は補償という別の手段で扱うと決められる
- 依頼を DB に残す形なら、確定した依頼はプロセスが止まっても失われない

---

### 欠点

範囲を狭めると、トランザクションの外に出した処理を状態と再送で扱います。そのため、次の制約があります。

- 注文が `pending_payment` のまま残る時間が生まれ、その状態を画面と集計の両方で扱う必要がある
- 依頼を中継プロセスに預けると、業務と直接関係のない表とプロセスを運用し続ける
- 呼び出し先が重複排除に使える識別子や仕組みを提供していない場合は、ローカルの DB だけで重複した外部の副作用を完全に防ぐことはできない。結果の照会や業務上の一意キー、補償処理などを組み合わせて扱う
- 外部の失敗を巻き戻しではなく、注文の状態遷移として設計し直す必要がある

---

### トランザクションを短くしても残るケース

- 複数のレコードを更新する処理どうしが、違う順序でロックを取る場合
- 画面の表示から更新までの間に人の操作を挟む更新
- 同じレコードへの更新が集中していて、範囲を狭めても待ちが積み上がる場合
- 読んだ値をもとに書き戻す処理で、同時実行の異常が結果に現れる場合

複数のレコードのロック順序が逆になる問題は、トランザクションの範囲を狭めても消えません。同じ 2 件を逆の順で更新する 2 本は、互いの解放を待ってどちらも進まなくなります。順序を揃える方法は Deadlock で扱います。

人の操作を挟む更新では、操作を待つ間トランザクションを開いたままにせず、表示した時から値が変わっていないかを更新の時に検査します。読んだ時のバージョン番号を更新条件に入れ、値が変わっていたら弾く方法（楽観ロック）が使われます。

更新が特定の 1 件に集中する問題は、範囲を狭めるだけでは解消しないため、更新を 1 件に集めない設計に変えます。例えば、人気商品の在庫を 1 件で持たずに複数のレコードに分けて引き当て、その合計を在庫数とします。読んだ値をもとに書き戻す時の異常と分離レベルの関係は Transaction Isolation の題材です。
