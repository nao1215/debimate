# 決定の記録（技術ノートの面白さの改善）

採点・案作り・書き直しをする全員が、最初にこのファイルを読む。基準は rubric.md・stage2_brief.md・debimate-visual-notes スキルの「面白さの観点」にだけ置き、指示文に書き足さない。変える時はこのファイルに日付と著者の言葉を足してから、該当のファイルを直す。

## 2026-11-11（著者の指定）

1. 面白さ = 意外性（直感に反する挙動）× 具体性 × 独自性 × 読者との関連性。原典を丁寧に説明するのは正しいが、面白さにつながるのは現場の経験。経験は捏造せず、weeknotes・実在の障害報告・手元の実験で補う。
2. 精査の軸: 上から読んで理解しやすいか、読者を引きつけるフック、読後に持ち帰れるもの、事実、サイトを回遊したくなるか、debimate-visual-notes どおりで作者のカラーが出ているか。
3. 実験的なコードは図示できた方が強い。図とコードを併記した方がよいケースもある。
4. 基準の記事: 上（5）は Wallet と Transaction Scope、中（3）は Quorum、下（1〜2）は Adapter と Sidecar。
5. Wallet が良いのは、最初に知りたい内容を箇条書きで挙げてから書いたことと、競合との比較を明確に示したこと、debimate-visual-notes で書いたこと。古い create-tech-notes で書いたノートはテンプレ感が強い。
6. 点が低いのは、create-tech-notes 時代に書いて最後の流れが強引だから。利点・欠点が必ず出て、その技術を使いたい・出会った読者の心を掴んでいない。
7. 点の低い記事は、同じ題材の人気記事（はてブ・HN など）がなぜ人気かを分析する。構成自体が変わってよい。
8. Bounded Context など DDD のノートも、駄目なら直してよい。
9. 点の低いものは全カテゴリが対象。ブロックチェーンと LLM（実務でよく読まれる）を優先してよいが、全部直すので順番は入れ替わってよい。総合 2 は先に直して無くす。
10. 評価基準や修正方法がブレることを避ける（コンテキストの蓄積、サブエージェントの使用による）。今まで文章を直してきたのに質の低いものが残っている。
