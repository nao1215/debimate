# 文体ガイド（debimate 技術ノート / content/notes）

`content/notes/` 配下の技術ノート (です・ます体) を書くときの文体・装飾・表記の規約。debimate の技術ブログ記事 155 本を実測した結果と、既存の `content/notes/*/_index.md` の文体を突き合わせて言語化したもの。

このガイドと本人の実文を参照して書き、omokage は補助的な分布の確認に使う。文体の判断は、語彙・主語・述語・段落の接続を本人の用例と比較して行う。

2026-11-03 ユーザー指定：omokage は補助であり、得点だけでは本人の文体との一致を判定しない。本人の最近の実文と、`voice_samples.md`・`voice_markers.md`・用語資料を照合し、頻用表現、語と動詞の組み合わせ、主語の選び方を全文で確認する。読者の気持ちを推測する前置き、抽象名詞を重ねた説明、同じ内容の言い直しは、具体的な処理・対象・結果を述べる文に直す。「この構造を知りたくなる場面の代表は〜」のような文を、用途を説明したことにしない。必要な専門用語・成立条件は保つ。

確認結果には、参照した本人の用例、記事の該当文、残す／直す理由を記録する。「全文を読んだ」「高得点だった」だけで文体確認を完了しない。「半分ぐらい」はユーザーによる効き目の評価であり、50%ずつ配点する採点規則ではない。

**このガイドより先に読む物が 2 つある。**

- `voice_samples.md` — 本人の地の文の実例。文体はここで掴む。**このガイドの地の文（である体の指示文）は手本にしない。** 規則を読んで書くと、規則を守った別の文体ができる
- `voice_markers.md` — ノート側だけで増えた言い回しの実測表。規則を足す度にノート専用の方言が育ち、10 日で本人の 10 倍の密度になっていた（2026-08-18 ユーザー指摘）。omokage は分布を見るため、この種のズレはスコアを保ったまま残る

## 1. ノートとブログ記事の書き分け

同じ です・ます体でも、ブログ記事とノートでは温度が違う。

| | 技術ブログ記事 (`content/post/ja/`) | 技術ノート (`content/notes/`、このガイドの対象) |
|---|---|---|
| 目的 | 作った話・調べた話の読み物 | 後から引くリファレンス |
| 文体 | です・ます体 | です・ます体 (同じ) |
| 一人称 | 「私」を積極的に使う | ほぼ使わない |
| 自虐括弧 | 最大の癖。多用する | 使わない |
| 私的余談 | 転職・前職・家庭の話が織り込まれる | 入れない |
| 締め | `### 最後に` で所感・こぼれ話 | 締めのセクションを作らない |
| 見出し | `### 前書き：〇〇` `### 最後に` | `### なぜ〇〇が必要なのか` `### 仕組み` `### 利点` `### 欠点` |

ノートはブログの「体験の記録」ではなく「定義と構造の記録」である。エッセイ要素を抜き、下層の癖 (接続詞の選び方・括弧への情報の詰め方・断定の濃度) だけをブログから引き継ぐ。

一方で、リファレンスだからといって である体には倒さない。`content/notes/*/_index.md` は既に です・ます体で書かれており、サイト内の文体を揃える意図がある。omokage の `nao-tech` プロファイルも です・ます体で学習されているため、である体で書くとスコアが 0% になる。

## 2. 文体の核

1. 文末は です・ます体で通す。である体を混ぜない。
2. 一人称は「私」。ただしノートではほぼ登場しない。「僕」「筆者」「自分 (一人称として)」は使わない。
3. 見出しは `###` (h3) が主。小分類だけ `####` (h4)。h1/h2 は本文に書かない (タイトルは front matter)。
4. 各 `###` セクションの末尾に `---` (水平線) を置く。最後の h3 の後ろには置かない。
5. 見出しの直下にリード文 (「本セクションでは〜を説明します」) を置かない。次の行はいきなり第1文から入る。
6. 太字 `**...**` を本文の強調に使わない。概念名は「」で囲む。強調したくなったら見出しか箇条書きで構造化する。
7. 助詞「を」の直後に読点「、」を打たない。「〜を、確認します」は禁止。語順を変えて回避する。
8. 1段落 1〜4文。5文を超えそうなら分割する。
9. 断定を続けすぎない。「〜と考えられます」「〜と言えます」「〜のではないでしょうか」を記事に2〜4回混ぜて緩衝する。
10. 略語・専門用語は初出で括弧書きの英日併記で補足する。「コンセンサス (合意、consensus)」のように。
11. 数式は LaTeX ではなくインラインバッククォート。KaTeX が未設定のため `$\mu$` は表示が崩れる。
12. 自己言及は「本記事」で書く（2026-11-02 更新。著者が調整した Wallet ノートと debimate-visual-notes スキルに合わせた）。「本ノート」「このノート」「この記事」「本稿」は使わない。「本記事では」は導入で 1〜2 回までにし、節ごとに繰り返さない。front matter の `series` は構造化メタなので対象外。
13. 他のノートを指す時は「Domain Event のノート」のように「〜のノート」で書くか、リンクを本文の語句に埋める（「[Finality](../finality/)で扱っている区別です」）。2026-08-10 の「ノートを記事と呼ばない」は、他のノートを「〜の記事」と呼ぶ形にだけ残す。`scripts/style_check.sh` が検出する。
14. 体言止めオチ (「無用の長物。」) を使わない。述語まで書く。
15. 顔文字・絵文字は使わない。
16. 時点情報 (「（2026 年時点）」) は使わない。バージョン依存の挙動は「etcd 3.5 では〜です」のように事実として淡々と書く。

### 緩衝表現の使い分け

緩衝表現は「具体的かつ判断の余地がある主張」にだけ付ける装置である。

良い例:

```
リーダー選出のタイムアウトを短くすると、障害検知は速くなります。
ただし、ネットワークが一時的に詰まっただけで再選出が走るため、
運用のばらつきが大きいクラスタでは長めに取る方が安全だと考えられます。
```

避ける例 (中身の薄い格言に緩衝を貼ったもの):

- 「分散システムを理解する事はトレードオフを理解する事と言い換えてもよいと考えられます」
- 「アーキテクチャは本質的にコミュニケーションの問題であると言えます」

こうした大言壮語は、緩衝で和らげるどころか幼稚さが増幅されます。書きたくなったら、具体的な構成要素を列挙して言い切る形へ置き換えてください。

## 3. べからず集

本人が記事「あなたの文章が読みたい」「omokage を作った話」で LLM 文章への拒否反応を明言している。以下は避ける。

| 避けるもの | 理由・代替 |
|---|---|
| 構造化された箇条書きの乱用 | 本人が最も嫌う。地の文で書くべき説明を箇条書きに分解しない。箇条書きは実際に列挙すべきもの (機能・手順・比較項目) だけに使う |
| 無駄に長く中身のない文章 | 同じ事を言い換えて水増ししない。1段落で言える事は1段落で書く |
| 太字の乱用 | 地の文の強調太字は使わない。強調は「」か地の文の言い回しで |
| 不要な横文字 | 「ソリューション」「リードする」のような意識高い横文字を避ける。日本語で書けるものは日本語で |
| 情緒的・大げさな形容 | 「素晴らしい」「強力な」「革命的」「驚くべき」を避ける。中立に書く |
| LLM っぽい締め | 「いかがでしたか」「お役に立てれば幸いです」「ぜひ参考に」「最後まで読んでいただきありがとうございました」「次のステップ」を使わない |
| 「まとめ」見出しでの箇条書き再掲 | 本論を箇条書きで要約し直す締めを作らない。ノートは最後の技術セクションでそのまま終える |
| 「ざっくり」 | 本人が使わないと明言。「大まかに」「要点だけ言うと」か、前置きなしで言い切る。「大雑把に言えば」も同様に避ける |
| 「実務では」「業務では」「現場では」 | 本人が使わないと明言。主語をぼかした一般化を避け、事実として淡々と言い切る |
| 過剰な前置き・宣伝文句 | 「初心者にも分かりやすく」「徹底解説」のような煽りを付けない |
| 「〜のイメージ」「〜みたいな感じ」「〜っぽい」 | 曖昧で、定義としては不十分 |
| 料理・スポーツ・日用品に例える比喩 | 本人は 221 本の記事で一度も使っていない。技術文書として浮く |
| 音楽バンド・洋ドラ・ゲームの比喩、家族や生活のネタ | ブログでは頻出だが、ノートには持ち込まない |
| 「以上、〜について解説しました」 | 締めのセクション自体を作らない |
| 文末「〜で。」 | 助詞「で」+句点の終止。「〜で確認します」のように述語まで書く |
| 「〜と言えます」で事実を包む | 仕組みの説明は事実なので言い切る。緩衝は判断が入る主張にだけ付ける（→ §11） |
| 「〜する形です」「〜という装置です」「〜にあたります」 | 名詞へ言い換えず、主語と動詞で普通に書く（→ §11） |
| 「〜の側」（動作主体を指す場合を除く） | 「側」を外して主語を名指しする（→ §11） |
| 「〜として知られています」「〜と言われています」 | 伝聞・権威付けで濁さず、事実を短く言い切る |
| 「そもそも」 | 使わない。前置きなしで本題を書く |
| 運用・実務の経験談 | 書き手は運用経験を語る立場にない。「運用でよく踏みます」「本番では〜」は書かない |
| 読者が知らない固有名詞の羅列 | 製品名を並べても、知らない読者には情報がゼロになる（→ §12） |

比喩を使うなら、本人が実際に使う型に寄せる。「同じ仕組みを持つ別の技術との対比」「規格・実装に基づく対比」「既存ノートとの対比」の3つが安全である。

- 「これは [X] と同じく〜です」
- 「[X] と発想は同じです。〜する点だけが違います」
- 「[X] を1台に閉じ込めた形と見る事もできます」

過去記事に用例が無いカタカナ語 (「レプリケーション」「スケーラビリティ」「マイクロサービス」など分散システム・アーキテクチャ系の語彙はほぼ未使用) は、上の長音省略ルールを適用して決める。「スケーラビリティ」「セマフォ」「ミドルウェア」のように語尾の長音を落とす。

ブロックチェーン系のノートでは、ブロックの列を「鎖」ではなく「チェーン」と書く (2026-08-10 ユーザー指摘)。白書の引用を訳す時も chain は「チェーン」と訳す。

### 略語 vs 正式名称

短く定着した略語は略語、概念語はカタカナ正式形を使う。

| 採用 | 不採用 | 実測 |
|---|---|---|
| DB | ~~データベース~~ | 131 : 15 |
| PR | ~~プルリクエスト~~ | 略語優勢 |
| OS | ~~オペレーティングシステム~~ | 略語優勢 |
| コマンド | ~~cmd~~ | カタカナ |
| ディレクトリ | ~~dir~~ | カタカナ |
| リポジトリ | ~~repo~~ | カタカナ |
| バージョン | ~~版~~ | 126 : 0 |
| アドレス | ~~住所~~ | ネットワークの宛先は「アドレス」 |
| 現実的 | ~~実際的~~ | 13 : 0 |
| コスト | ~~費用~~ | 29 : 14 |

「版」は書籍の『第 2 版』のような刊行形態にだけ使う。ソフトウェアやイメージの version は「バージョン」と書く。「コンテナの版の組み合わせ」のような書き方は、読者が「版とは何か」で止まる。`scripts/style_check.sh` が検出する。

「コスト」も同じ扱いで、実装や保守の手間を指すなら「費用」ではなく「コスト」を使う。成句の「費用対効果」だけは残す。横文字を避ける方針 (§3) と衝突するように見えるが、避ける対象は「ソリューション」「リードする」のような言い換え可能な意識高い語であって、実測で定着している外来語は対象外である。判断は本人の用例の多い方に従う。

「DB」は初出で「DB (データベース)」と展開してから略語で通すと読者に優しい。ノートは初見の読者が来る前提なので、略語の初出展開はブログ記事より丁寧にしてよい。

### 英語のまま書く語 vs カタカナに開く語

判断基準は「その語は特定言語・特定製品の識別子やキーワードか、それとも日本語に定着した一般外来語か」である。

- 英語のまま: 言語固有の型名・キーワード・概念名 (`Context` 67 : コンテキスト 18、`goroutine` 3 : ゴルーチン 0、`channel` 6 : チャネル 1)。プロトコル名・アルゴリズム名 (Raft、Paxos、gRPC、CRDT) も英語
- カタカナ: 日本語に定着した一般外来語 (インターフェース 86 : interface 34、ユーザ、ディレクトリ、メモリ、コマンド)
- コード上の識別子・API 名はバッククォートで囲む (`` `context.Context` ``、`` `AppendEntries` ``)
- mermaid 図に登場人物として名前を付けた役割は、地の文でも同じ英語で通す (Leader / Follower / Holder / Grantor / Monitor)。図が `Leader` で地の文が「リーダー」だと、読者は対応を変換しながら読む事になる。クライアント・サーバのような一般外来語はカタカナのまま

omokage スコアのために技術用語をカタカナへ変換しない。英字が地の文に増えると hiragana 比率でスコアが下がる事があるが、それは nao の素の文体の結果であって、直すべきズレではない。

## 6. 記号・括弧・数字

- 三点リーダ: 全角「…」を基本とする
- 感嘆符・疑問符: 日本語文中では全角「！」「？」。半角はコード内のみ
- 波ダッシュ: 「〜」(U+301C)。全角チルダ「～」(U+FF5E) ではない
- 括弧: 日本語文の中では全角「（）」、英数字・コード片を囲うときは半角「()」。1段落内では揃える
- カギ括弧: 強調・概念提示・引用は「」。書籍/曲/記事タイトルは『』。地の文の強調に『』は使わない
- 数字: 本文中は半角

括弧の中身は捨ててよい余談ではなく、本体並みの情報密度を持たせる。ノートでの典型用法は次の通り。

- 専門用語の英日併記: 「コンセンサス（合意、consensus）」
- 略語の展開: 「2PC（Two-Phase Commit、2 相コミット）」
- 但し書き: 「（ネットワーク分断が起きていない場合）」
- 条件の添加: 「（過半数のノードが生存している事が前提）」

括弧の中は です・ます体にしない。名詞句か言い切りで書く。

- 修正前: 「生存時間を指定して lease を作り（実際の長さはサーバが決めます）、」
- 修正後: 「生存時間を指定して lease を作り（実際の長さはサーバが決める）、」

括弧の中に 1 文まるごと入れたくなったら、括弧を外して独立した文にする方が読みやすい。

- 修正前: 「順序を表す通し番号（index。DB の索引とは無関係の、ログの中での連番です）」
- 修正後: 「順序を表す通し番号（index）と〜。index はログの中での連番で、DB の索引とは関係がありません。」

ブログで多用される自虐落ち (「（私だ）」「（戒め）」) や笑い系 (「（個人の感想です）」) はノートには入れない。

## 7. 接続詞・常套句

### 積極的に使う

| 語 | 用法 |
|---|---|
| ちなみに | 補足・関連知識の挿入 |
| そのため | 因果 |
| ただし / ただ | 留保・例外 |
| しかし | 強い逆接。本人の逆接の主力で、実測では「ただし」の 4.5 倍使う。「使ってよい」ではなく、前の文を正面から否定する所では「ただし」ではなくこちらを選ぶ（「しかし、TCP 接続監視では適切に障害を検知できないケースがあります」） |
| その結果 | 前段の帰結を受ける。因果が読み取りにくい所には必ず置く |
| 一方で / その一方で | 対比 |
| とは言え / とはいえ | 自己反論・留保 |
| なお、 | 補足・注記 |
| 一般に / 通常 / 教科書的には | 一般原則の提示 |
| つまり / 言い換えると | 言い換え・要約 |
| 逆に | 定義の裏返し、対立概念の導入 |
| 以下の通りです / 以下が〜です / 以下のような〜があります | リスト・表・図の直前の橋渡し。本人はこの 3 つで受ける。「〜を以下に示します」は本人も使うが、ノートでの密度が実測で 11 倍になっていたので、同じ型を続けない（→ `voice_markers.md`） |
| 〜筈（はず） | 推量で断定を弱める |

### 避ける

| 避けるもの | 理由・代替 |
|---|---|
| そもそも | 前置きとして機能していない。削って本題から書く |
| では / さて / ところで | 段落転換に接続詞を使わない。白行・水平線・新しい見出しで処理する |
| 「例えば」の連続 | 本人の頻用語なので、使う事自体は避けない（実測でノートの 1.7 倍使う）。避けるのは 2 段落続けて同じ語で例示を始める形で、「具体的には」やコロン形式へ散らす（→ 下の「具体例の出し方」） |
| また（多用） | 「加えて」「さらに」を混ぜるか、箇条書きに切る |
| まずは / 次に / 最後に（手順以外で） | 番号付きリストか `####` で構造化する |
| ならば / それならば | 使わない。読者の反論を書くなら「〜と考える方がいるかもしれません」から直接始める |

接続詞は段落の頭で1つだけ。同じ段落内で複数の接続詞を重ねない。

### 具体例の出し方

具体例は、例だと分かる書き出しから始める。技術記事 156 本の実測でも、例えば 89、具体的には 33、一例 9、「（例：ブルートフォース）」の括弧形式が使われている。

一般論の説明の直後に具体値だけが続くと、読者はその値を仕様として読んでしまう。書き出しに1語あるだけで、値が例示だと伝わる。

- 修正前: 「1 秒ごとに信号を送り、5 秒間受信が無ければ故障とみなす、といった設定になります」
- 修正後: 「具体的には、1 秒ごとに信号を送り、5 秒間受信が無ければ故障とみなす設定です」

書き出しの使い分けは次の通り。

| 書き出し | 使う場面 |
|---|---|
| 例えば、 | あり得る選択肢の中から1つを挙げる |
| 具体的には、 | 直前の抽象的な説明を、そのまま具体化する |
| 一例として、 | 代表例を1つだけ示す |
| （例：〜） | 文の途中や表の中に短く添える |

「〜といった設定になります」「〜みたいな形です」で例示を後付けしない。文末で example だと分かっても、読者は既に仕様として読み進めている。

## 8. 図・表・コードの方針

- mermaid を主力にする。構造は `flowchart`、時間軸のあるやり取りは `sequenceDiagram`、状態遷移は `stateDiagram-v2`。詳細は `mermaid_recipes.md`
- 図の直前に「何を見ているか」を1行書く。図を置いて説明を省かない
- 図の直後は、結果・補足を別段落で受ける。図の直後にいきなり次の見出しへ飛ばない
- 比較・分類・トレードオフの一覧は表にする。mermaid で無理に描くより読みやすい
- コードは概念の理解に必要な時だけ短く載せる。言語指定を必ず付ける
- 「コードや図ばかりで文字が薄い」も「文字だらけで図が無い」も避ける
- 表の直後に空行を置く。忘れると次の段落が最終行へ吸い込まれ、1 列だけ多い行になる（`scripts/style_check.sh` が列数の不揃いを検出する）
- リスト記号はハイフン `-` で統一する。アスタリスク `*` は使わない
- リスト・表・コードの直前に説明文を1行置く

### 図の並び順と、本文で列挙した順を揃える

図の中の要素を本文で列挙する時は、図と同じ順で並べる。2026-08-08 の Anticorruption Layer ノートでは、3 つの責任を本文が「API を呼ぶ部分 → 翻訳 → インターフェースを満たす部分」の順で挙げ、図は上から「インターフェースの実装 → 翻訳 → クライアント」と逆順に並べていた。読者は 3 つの対応を頭の中で反転させながら読む事になる。

橋渡し文に「上に挙げた順で」と書くと、対応が取れている事が読者に伝わる。順序を揃えられない図なら、本文の列挙に図のノード名 (`Checker` など) を添えて、どれの話かを名前で結ぶ。

### 図ごとに矢印の意味が変わるなら、その場で断る

1 本の記事に、呼び出しの流れを描いた図と、コードの参照の向きを描いた図が混ざる事がある。断らずに置くと、後の図を受ける「参照する矢印は 1 本も無く」という文が、前の図と矛盾して見える。

図の橋渡し文で「図の矢印は、呼び出しの流れではなく、コードがどちらを参照するかの向きです」と 1 行書く。図の中に注記を足すより、直前の文で断る方が読み飛ばされにくい。

### 表の行見出しと、直前の本文の軸を揃える

比較表は本文の主張を圧縮した物なので、行見出しの選び方が本文と食い違うと、読者は表の側を信じる。2026-08-08 の Ambassador ノートでは、本文が「通信の向きでは切り分けられません」と書いた直後の表に「アプリケーションの役割｜外へ出て行くクライアント｜外から見られるサーバ」という行があり、方向で切り分ける基準へ戻っていた。

書き上げたら、表の行見出しを 1 つずつ読み、直前の段落が否定した軸が混ざっていないかを確かめる。混ざっていたらその行を削る。表を残して本文を変えると、本文の判断が表の都合で歪む。

行見出しと中身の対応もずれやすい。「単純化する相手」という見出しに対して中身が「外から見たアプリケーション」だと、相手（受け取る方）ではなく対象（単純化される方）が書かれている。見出しを読んでから中身を読み、格が合うかを確かめる。

## 9. 段落と改行

- 段落は 2〜4 行 (80〜160 字) の塊にする。下限と上限の両方があり、どちらを外しても読みにくくなる
- 1 行だけの段落を並べない。1 文で切って改行を挟むより、隣の段落へ寄せる（例外は図・表・コード直前の橋渡し文）
- 200 字を超えたら、その段落を読み直す。閾値で機械的に割るのではなく、話題が 2 つ入っているかで判断する。入っていれば切れ目で割り、1 つなら残してよい。引用は英語と訳の両方を書くので伸びるし、コードを説明する段落は識別子で伸びる。本人のノート 48 本では 200 字超が 1 本あたり 0〜10 段落あり、最長の中央値は 242 字である。違反として扱うのは 300 字超で、`scripts/style_check.sh` はそこだけを `[NG]`、200 字超は `[INFO]` で出す
- 1段落 1〜3文を基準にする。ただし、これは行数を満たした上での目安である。文数を守るために 1 行の段落を量産しない
- 段落が長くなりそうなら「定義」「例」「補足」のどれかで切る
- 単文段落 (1文だけ) は、強調・転換のリズムを作る意図がある時だけ使う。記事内 1〜3 回まで。意図の無い短い段落は上のルールに従って隣へ寄せる
- 段落の話題転換は白行のみで行う。「では」「さて」のような転換接続詞は使わない
- 「ここでは」「以下では」を段落の先頭に置かない。技術記事 156 本の実測で、行頭に「ここでは」が来る例は 0 件である。直前の文に続けて同じ段落の中で書く
- `###` セクションの末尾に `---` を置く。最後の h3 の後ろには置かない

「ここでは」は、直前で述べた対象を受けて範囲を限定する語である。段落を改めてから書くと、受けるはずの対象が前の段落へ離れてしまい、限定が宙に浮く。

- 修正前: 「ハートビートは〜する仕組みです。」（改行）「ここでは、停止する故障だけを扱います。」
- 修正後: 「ハートビートは〜する仕組みです。ここでは、停止する故障だけを扱います。」

文のリズムは「結論を独立1行で言い切る → 改行 → 読点で繋ぐやや長めの説明文」が基本形である。

図・表・コードの直前に置く 1 行の橋渡し文（「読み取りと書き込みが重なるのは、次の 3 通りです。」）は、2 行ルールの例外である。ここを隣へ寄せると、図が段落の途中に挟まって読みにくくなる。`scripts/style_check.sh` の「2 行以下の段落」も、次が図・表・箇条書きの段落は除外している。

### 段落が膨らむのは、書き足す時である

初稿で 400 字の段落を書く事は少ない。膨らむのは、査読の指摘や後から思い付いた補足を、既存の段落の末尾へ継ぎ足していく時である。書き手には元の段落が話題の置き場所に見えるため、1 件ずつ足しても違和感が出ない。2026-08-08 の Merkle Tree ノートは、査読を 2 巡通した結果、14 本の中で最も段落が長くなった（平均 207 字、最長 540 字）。

書き足す時は、次のどれかを選ぶ。段落の末尾へ足すのは、足す内容が元の文の直接の言い換えか補足である場合だけにする。

- 元の文を差し替える（指摘が「その記述が誤り」なら、足すのではなく直す）
- 段落を割り、新しい話題として書く
- `###` か `####` を 1 つ作る（1 段落で収まらないなら、それは節である）

割る時に 2 つ注意がある。第一に、後半が「ここでは」「以下では」で始まらないようにする。範囲の宣言には「ここでは」を付ける（→ §14 型1）一方で、この語は段落の先頭に置かない（→ 上）ので、割る位置によっては 2 つの規則が衝突する。文の途中へ移して「〜は、ここでは〜」と書けば両方を満たせる。

第二に、長い引用を含む文は割れない。1 文が丸ごと 200 字を超える場合、直す先は段落の切り方ではなく引用の長さである。引用を、その段落で効いている部分だけへ狭める。

ここで引用を独立した段落へ追い出すと、地の文の無い浮いた行ができる。読者は、その引用を誰が何のために出したのかを自分で補う事になる。2026-08-19 の idempotency で、200 字を守るために次の形を作って指摘を受けた。字数の規則は、引用を地の文から切り離す理由にならない。

- 修正前（引用だけの行）: 「[the intended effect on the server ...](URL)」（同じ要求を複数回送った時にサーバへ意図される結果が、1 回送った時と同じ）
- 修正後（地の文に埋める）: 定義は、「[the intended effect on the server ...](URL)」（同じ要求を複数回送った時にサーバへ意図される結果が、1 回送った時と同じ）と書かれています

## 11. 事実は言い切る（緩衝表現と名詞化）

ノートで最も指摘されやすいのが、断定を避けて文を膨らませる癖である。仕組みの説明は事実なので、そのまま言い切る。

### 緩衝表現を付けてよい所、駄目な所

緩衝表現（「〜と言えます」「〜と考えられます」「〜のではないでしょうか」）は、判断の余地が残る主張にだけ付ける装置である。仕組みが何をしているかの説明に貼ると、書き手が自信を持てていないように読める。

| | 例 | 判定 |
|---|---|---|
| 仕組みの説明 | ハートビートは、この曖昧さを判定可能な形へ落とし込んでいます | ○ 言い切る |
| 同上に緩衝を貼る | 〜判定可能な形へ落とし込む装置と言えます | ✕ |
| 運用上の判断 | 遅延のばらつきが大きい環境では固定閾値より扱いやすいと考えられます | ○ 緩衝してよい |
| 中身の薄い格言 | 分散システムを理解する事はトレードオフを理解する事だと言えます | ✕ そもそも書かない |

記事全体で 2〜4 回が目安である。「事実の説明に 1 回も付いていない」が正しい状態で、緩衝が必要になるのは判断を書いた時だけと考えてよい。

読者がどうであるかは、仕組みの説明とは別の層にある。読者の経験・きっかけ・関心を書く文は観測できない事を述べているので、言い切らずに緩衝を付ける。ここは §11 が消そうとしている緩衝ではなく、付けるのが正しい数少ない箇所である（2026-08-11 の query-processing で指摘）。

| 修正前 | 修正後 |
|---|---|
| 開発者がこの仕組みへ最初に触れるのは、応答の遅い問い合わせを調べる場面です | この仕組みの名前を最初に見るのは、応答の遅い問い合わせを調べている時の実行計画の中です |

同じ段落の中でも、続く「`EXPLAIN` と打つとこう出る」は観測できる事実なので言い切る。1 文ごとに、書いているのが仕組みか読者かで切り替える。

### 名詞へ言い換えない

「〜する形です」「〜という装置です」「〜にあたります」のように、動作を名詞へ言い換えると文が遠回りになる。主語と動詞でそのまま書く。

| 修正前 | 修正後 |
|---|---|
| 閾値を利用側が選ぶ形です | 閾値を利用側が選びます |
| 障害検知は、こうした復旧処理の全ての入口にあたります | 障害を検知できれば、復旧処理を開始できます |
| ハートビートは、その割り切りを最小のコストで実現する形だと言えます | ハートビートは、最小のコストで割り切りを実現しています |
| 実装としてはハートビートで Lease を更新する形が多く | 実装ではハートビートで Lease を更新する事が多く |

### 「〜の側」で主語をぼかさない

名詞に「側」を付けても情報は増えず、誰が何をするのかがぼやける。対比したい時に付けたくなる語だが、対比は比べる対象を同じ形で並べれば付く。

| 修正前 | 修正後 |
|---|---|
| 速度の側から見ると | 速度の面では |
| 実装の側で制限を課す | 実装で制限を課す |
| `==` の意味は型の側が決める | `==` の意味を型ごとに定義できる |
| 判断は人間の側に残ります | 判断は人間に残ります |
| 規則の側は破れない | 規則が成り立ち続ける |

例外は「呼び出し側」「貸す側」のように動作主体を指す語と、「外側」「内側」のように方向を指す語である。判定は「側を外して文が成立するか」で行う。

### 伝聞で濁さない

「〜として知られています」「〜と言われています」は、事実を他人の口へ預ける言い方である。短く言い切る。

- 修正前: これは実装の工夫で解決できる話ではなく理論上の限界として知られています
- 修正後: これは実装の工夫で解決できません

### 「前者」「後者」で受けない

2 つ並べた対象を「前者」「後者」で受けると、読者は前の文へ戻って対応を数え直す事になる。名前をもう一度書くか、「1 つは〜。もう 1 つは〜」と番号で並べて、後の文で「2 つ目は」と受ける。

否定で説明するのも同じく遠回りになる。「〜の話ではありません」と言われても、読者には何の話なのかが残らない。何が起きるのかを具体的に書く。

- 修正前: 「時計の進む速さのずれに上限がある事と、Holder の停止や遅延が期限より短い事です。後者は時刻の話ではありません。GC 停止や仮想マシンの一時停止では時計は正しく進んでおり、破れているのは「期限内に処理を終える」という仮定の方です」
- 修正後: 「1 つは、貸す側と借りる側で時計の進む速さのずれに上限がある事。もう 1 つは、Holder が期限内に処理を終える事です。2 つ目の仮定は簡単に破れます。GC 停止や仮想マシンの一時停止で Holder が数十秒止まると、期限を過ぎた後に書き込みが実行されます」

同じ規則が mermaid 図の `Note` にも掛かる。図の中は文字数が限られるため、否定形で書くと読者が残りを組み立てる余地しか残らない。原因と結果をそれぞれ名指しする。

- 修正前: `Note over L,W: 原因を作っていないのは<br/>Web サーバの方`
- 修正後: `Note over L,W: 原因はログ転送プロセス<br/>止まるのは Web サーバ`

`scripts/style_check.sh` が否定形の `Note` を `[INFO]` で出す。

### 比喩的な動詞を使わない

「剥がす」「握る」「寝かせる」「叩く」「運ぶ」のような比喩的な動詞は、何に対する操作なのかが読者に伝わらない。対象と操作を、その分野で通用する語で書く。

| 修正前 | 修正後 |
|---|---|
| 管理側がロックを剥がせばよい | 管理側がロックを強制的に解放すればよい |
| 強制的に剥がした場合に何が起きるか | 保持者の同意なしにロックを強制解放し、次のノードが取得した場合に何が起きるか |
| 管理側が剥がしたつもりでも、剥がされた側がそう認識していない | 管理側がロックを解放して Node B が取得しても、Node A 側の認識が変わらない |
| この方式は、集合が重なる性質に乗っています | この方式は、集合が重なる性質を利用しています |
| Lease も同じ土台に乗ります | Lease も同じ性質を利用しています |
| 拠点間の往復が待ち時間へ乗る | 拠点間の往復の時間が待ち時間へ加わる |
| 他の仕組みの土台に入ります | 他の仕組みの土台になります |
| 業務と関係のない仕組みを運ぶ事になる | 業務と関係のない outbox テーブルと relay プロセスを運用し続ける事になる |

判定は「その操作を実装するとき、どの API を呼ぶかが読み取れるか」で行う。読み取れないなら比喩になっている。

### 比喩的な名詞を使わない

動詞と同じ規則が名詞にも掛かる。資源や時間を「予算」と呼ぶと、上限なのか残量なのか許容値なのかが決まらない。測れる語で書く。

| 修正前 | 修正後 |
|---|---|
| 実行基盤から見ると同じ資源の予算を共有します | 実行基盤から見ると 1 つの資源の上限を共有します |
| 遅延の予算が厳しく、プロキシを 1 段挟む余裕が無い通信 | 許容できる遅延が小さく、プロキシを 1 段挟む余裕が無い通信 |

英語圏で resource budget、latency budget と呼ばれる概念でも、日本語のノートでは「上限」「許容できる遅延」へ開く。`scripts/style_check.sh` が「予算」を検出する。

負担を表す動詞にも同じ規則が掛かる。英語の carry を直訳した「運ぶ」「抱える」「背負う」は、読者に「利用する」とも「転送する」とも読める。維持し続ける負担を指すなら「運用し続ける」と書く。データを渡す意味の「運ぶ」（`種類は文字列で運びます`）は比喩ではないので、そのまま使ってよい。

「〜に乗る」「〜に入る」のように、性質や仕組みへの依存を移動の動詞で書くのも同じ問題を起こす。何をしているのかが「利用する」「前提にする」「土台になる」のどれなのかを決めて、その動詞で書く。

比喩を外すだけでは足りない場合がある。その対象が持つ操作の名前を、実装や仕様の用語に合わせる。ロックなら取得（acquire）と解放（release）で、受け渡す操作は無い。「別のノードへ渡す」と書くと、解放と取得の 2 段が 1 つの操作に見えてしまう。mermaid 図のラベルも同じ規則で書く。

### 目的語を落とさない

書き手には対象が自明なので、動詞だけを書いて先へ進んでしまう。読者は「何を」で止まる。2026-08-08 に本人から受けた指摘は、どれもこの形だった。

| 修正前 | 読者の疑問 | 修正後 |
|---|---|---|
| 監視基盤が一定間隔で取りに来る形が多くなります | 何を取るのか | 監視基盤が一定間隔でメトリクスを取りに来る形が多くなります |
| ライブラリで解く方法もあります | 何を解くのか | この判断と設定をクライアントライブラリへ任せる方法もあります |
| 日付とレベルの書き方がまちまちなログ | 何のレベルか | 日時とログレベルの書き方がまちまちなログ |

判定は「その文だけを取り出した時、動詞の対象が復元できるか」で行う。同じ対象を続けて指す 2 回目以降は省いてよい。落としてよいのは、直前の文で名指しした対象だけである。

### 抽象名詞と指示語で対象をぼかさない

「極端」「位置」「状態」のような抽象名詞や、「こちら」「この 2 つ」のような指示語で対象を指すと、読者は何を指しているのかを自分で組み立て直す事になる。本文で既に出した名前か数値へ置き換えられるなら、置き換える。

| 修正前 | 修正後 |
|---|---|
| 成立に必要な応答数の選び方には、2 つの極端があります | 成立に必要な応答数は、1 台から N 台までのどこかを選ぶ事になります |
| 過半数を要求する構成は、この 2 つの間に入ります | 過半数は、1 台と N 台の中間にあたります |
| 重なったノードだけは両方を知る位置に居る | 2 つとも受け取るのは重なったノードだけ |
| 上流の採番規則がこちらの実装へ染み出す | 上流の採番規則が下流の実装へ染み出す |

「こちら」「そちら」「あちら」は特に危ない。ノートは読者を登場人物の立場に置いていないため、指す先が原理的に決まらない。`scripts/style_check.sh` が検出する。

集合や確率のような数学的な性質も、抽象語のままだと追えない。最小の具体例で数えて見せると、性質と理由が同時に伝わる。

- 修正前: 「過半数の集合は、どの 2 つを取っても必ず 1 台以上を共有します」
- 修正後: 「5 台から 3 台を選び、別の操作がまた 3 台を選ぶと、合わせて 6 台分を選んだ事になります。5 台しか居ないので、どちらの 3 台にも入るノードが 1 台以上残ります」

### 不可能と非推奨を区別する

「〜できません」「〜ません」と書いた箇所は、本当に不可能なのか、やると壊れるだけなのかを確認する。設計上の禁止を不可能と書くと、読者は「言語や仕組みが防いでくれる」と受け取る。

- 修正前: 「Aggregate は境界をまたぎません」（実際には、2 つの境界の型を材料にした Aggregate は書けてしまう）
- 修正後: 「Aggregate が 2 つの境界の型を材料にしている場合も同じ徴候で、どちらのユビキタス言語でも表せないモデルができています」

判定は「その状態を作るコードを書けるか」で行う。書けるなら、不可能ではなく徴候として書く。

### 英語の言い回しを直訳のまま置かない

原典が英語の場合、慣用表現を語ごとに移すと日本語として浮く。意味を取ってから日本語の言い方へ置き換える。引用符で囲んだ引用は原文に忠実でよく、直す対象は地の文での言い換えである。

| 原文 | 直訳 | 修正後 |
|---|---|---|
| simplifies the programmer's life | プログラマの生活を単純にする | プログラマの作業を単純にする |
| provides a less clean separation of concerns | 関心の分離としては綺麗さが劣る | 関心の分離が不十分になる |

判定は「その日本語を、英語の原文を知らない読者が自然に読めるか」で行う。`life` `clean` のような多義語ほど、辞書の第一義をそのまま置いて事故が起きる。

### 意味を分けて使っている 2 語を、関係を書かずに 1 文へ入れない

記事の中で役割を分けている 2 語がある場合、両方が出てくる文では 2 つの関係まで書く。書かないと、読者はその文で使い分けを推測する事になる。2026-08-08 の Anticorruption Layer ノートでは、「翻訳」を 2 つのモデルの間で意味を移す行為、「変換」を型や表現を機械的に移す作業として分けていたが、境界を説明する文で 2 つを並べただけになっていた。

- 修正前: 「意味を伴う変換までは翻訳の仕事です」
- 修正後: 「意味を伴う変換までが翻訳で、ACL の仕事です」

使い分けそのものは、両方が初めて要る箇所で 1 度だけ示す。節をまたぐたびに説明し直すと、今度は §14 の「くどくしない」に当たる。

### 説明的な言い回しより定着した用語

自分で言葉を作らず、その分野で通用する語を使う。

- 修正前: 全員が全員を見る構成
- 修正後: 相互監視の構成

## 12. 固有名詞の扱いと、書いてはいけない事

### 読者が知らない固有名詞を並べない

製品名・実装名を並べても、それを知らない読者には情報がゼロになる。理解に必要でないなら書かない。

- 削除された例: 「Raft の `AppendEntries`、Kubernetes の kubelet が更新するノードステータス、Cassandra の gossip など、実装は違っても発想は同じです」
  - 理由: Raft や Kubernetes を知らないと読めない。この一文が無くても本文の理解は進む
- 削除された例: 「Cassandra や Akka が採用しており、遅延のばらつきが大きい環境では〜」
  - 理由: 採用例は本文の理解に効いていない。後半の判断だけ残せばよい

比較表の「代表例」列のように、引くための情報として並べるのは問題ない。地の文で説明の代わりに製品名を出す事が駄目である。

### 出すなら、何をするものかを説明する

初めて見る固有名詞は、名前を出しただけで説明した気にならない。1〜3 文で「何をするものか」を書く。

- 指摘: 「Phi Accrual Failure Detector は補足を書いて欲しい。初めてみた」
- 対応: 何を入力に取り、何を出力し、利用側がどう使うのかを段落で説明した

判断基準は「その語を知らない読者が、この段落を読んで意味を取れるか」である。取れないなら、説明を足すか、その語を消す。

### 人名には「氏」を付ける

本文で人名を出す時は敬称を付ける（2026-08-11 ユーザー指摘）。ノートは他人が書いた論文・資料・ブログを引いて成り立っており、呼び捨ては引用元への態度としてそのまま出る。日本語名・英語名のどちらにも付け、ハンドルネームも同じ扱いにする。

| 修正前 | 修正後 |
|---|---|
| Martin Fowler の [CQRS](URL) は | Martin Fowler 氏の [CQRS](URL) は |
| Evans の DDD Reference は〜と定義しています | Evans 氏の DDD Reference は〜と定義しています |
| Hayashibara らが 2004 年に発表した論文 | Hayashibara 氏らが 2004 年に発表した論文 |
| 解決策への糸口として ledsun の「〜」から | 解決策への糸口として ledsun 氏の「〜」から |

英語名は「Fowler 氏」と半角空白を挟み、日本語名は「和田卓人氏」と詰める。英数字と日本語が隣り合う所へ空白を入れる、という §6 の扱いに揃う。

付けない場所が 3 つある。書名・資料名・論文名の中に人名が含まれる場合（原題をそのまま書く）、引用文の中（原文へ手を入れない）、リンクの URL と front matter である。

`scripts/style_check.sh` が、これまでノートに出てきた人名を対象に検出する。一覧に無い人名は検出できないので、新しい人名を本文へ出したら、そのスクリプトの一覧にも足す。

### 検証しにくい記述は書かない

起源・最初の実装・普及の度合いは、一次情報に当たっても確定しない事が多い。読者が確かめられない記述は、正しくても価値が薄く、間違っていれば気付かれずに残る。書くなら一次情報へのリンクを添え、添えられないなら削る。

| 避ける書き方 | 扱い |
|---|---|
| 「〜自体の出典は 1989 年の論文です」 | 出典を確かめてリンクできないなら削る |
| 「〜が最初に提案しました」「〜が元祖です」 | 提案と実用化がずれる事が多い。削るか、論文名と発表年をリンク付きで書く |
| 「例外なく」「すべての実装が」 | 全称の主張は反例 1 つで崩れる。「主要な実装は」へ弱めるか、範囲を明示する |
| 「業界標準です」「デファクトです」 | 測る方法が無い。採用例を具体的に挙げるか、書かない |

論文の名前と発表年は、リンク先で確認できるなら書いてよい（→ §14 型4）。確認していない年号を添えない。

### 他システムの仕様は、書く前に一次情報で確かめる

etcd や Kubernetes のような外部システムの挙動を書く時は、公式ドキュメントか実装のコードを実際に開いて確認する。記憶や、それらしい要約のまま書くと、読者は嘘を持ち帰る。既定値・上限・API 名は特に外しやすい。

- 修正前: 「障害で空いたロックは既定で最大 1 分ほど他のクライアントへ与えません」
- 修正後: 「保持者の障害で空いたロックは、一定時間ほかのクライアントへ与えません（この待ち時間はクライアントが指定でき、上限は 1 分です）」
  - 論文の原文は「Clients may specify any lock-delay up to some bound, currently one minute」で、1 分は既定値ではなく上限だった

確認できない仕様は書かない。「〜という実装が多い」のように曖昧化して残すのも避ける。実装の詳細まで踏み込むと裏取りの負荷が上がるので、ノートの主張に効かない詳細は最初から入れない方が安全である。

### 1 つの製品の挙動を、そのジャンル全体の性質として書かない

普段触っている製品の挙動は、書き手にとって「当たり前」になっているため、一般論として書いても違和感が出ない。読者は別の製品を使っている。

2026-08-08、Sidecar ノートで実際に外した例を挙げる。どちらも Kubernetes では正しく、Amazon ECS では成り立たない。

| 書いた事 | 反例 |
|---|---|
| 障害の境界はコンテナごとに分かれる | ECS の `essential` は既定が true で、1 つのコンテナの停止が Task 全体へ波及する |
| 同じ実行単位のコンテナは localhost で呼び合える | ECS の Linux/EC2 での既定ネットワークモードは `bridge` で、別のアドレスになる |

対処は 2 つある。第一に、性質として書きたいなら「〜する設定なら」「実行基盤の設定によって」と条件を付ける。第二に、条件が付く事を読者が実感できるよう、反例になる製品を 1 つだけ具体例として出す。2 つ以上出すと製品比較の記事になる。

判定の手順は、「〜します」「〜できます」と書いた性質について、自分が普段使っていない実装を 1 つ選び、そこでも成り立つかを一次情報で確かめる事である。確かめられないなら、条件付きの書き方へ落とす。

主題そのものが抽象的なデータ構造やアルゴリズムで、製品ごとに実装が割れる場合は、反例を 1 つに絞る扱いでは足りない。「定義」「一般的な実装」「特定製品の実装」の 3 段を分けて書く必要があるので、`precision_claims.md` §10 を使う。

### 運用・実務の話は書かない

書き手は運用経験を語る立場にない。知らない事を書くと嘘になる。

- 削除された例: 「最後の点は運用でよく踏みます。〜Kubernetes が liveness probe と readiness probe を分けているのは、この区別を設定として表に出すためだと言えます」
  - 理由: 書き手が知らない話であるため

仕組みの性質として言える事（「信号が届く事しか保証しない」）は書いてよい。「運用ではこうなる」「本番では〜」という経験の語りが駄目である。

### 図を指すときは位置を明示する

図の直後の段落で図を受けるとき、どこを見ればよいかを書く。

- 修正前: 点線が途絶えた信号で、Monitor はこの不在だけを手がかりに〜
- 修正後: 上記の図の点線部分が途絶えた信号を表し、Monitor は信号の不着を手がかりに〜

ただし、指し方は図中のラベルか線種で行う。「左の経路」「右のノード」のように mermaid のレイアウトへ依存する位置で指さない。同じ `flowchart` でも `LR` と `TB` で枝の並ぶ向きが変わり、描画側の都合で入れ替わる事もある（2026-08-10、B-Tree ノートで指摘）。

- 修正前: 「上図の左の経路では、読むページ数が表の大きさで決まります。右の経路で決まるのは〜」（`flowchart LR` なので、2 本の枝は左右ではなく上下に積まれていた）
- 修正後: 「上記の図の索引なしの経路では、読むページ数が表の大きさで決まります。索引ありの経路で決まるのは〜」

どの図を指すかは「上記の図」「下記の図」で言う。「上図」「下図」は本人が 62 万字で 1 回しか書いていないので使わない（→ `voice_markers.md`）。止めるのは、1 枚の図の中を左右・上下で指す書き方である。ただし、図を受ける段落を毎回「上記の図の〜」で書き出さない。位置を指す必要がある所だけで使う（→ §25）。図中に指すためのラベルが無いなら、ラベルを足してから本文で呼ぶ。なお、キー順の「右端のページ」のように、図の配置ではなく対象そのものの性質を指す語は対象外になる。

### 読者への問いかけは、読者を主語にする

書き手が迷って見せる形は使わない。読者が抱きそうな疑問として書く。

- 修正前: TCP の接続断を見れば十分ではないか、と考えたくなります。ただ、これは両方向に外れます

### 冒頭のユースケースで、読者の経歴を決め付けない

特定の業務ドメイン（注文・決済・在庫）や職種や製品を、全員が通る道として書いてはいけない。その経験が無い読者は、冒頭で自分向けではないと判断する。

読者を主語にした「開発者がこれへ最初に触れるのは、〜する時ではないでしょうか」の形は、この失敗を招きやすいうえ、ノートをまたぐと同じ文が並ぶ。2026-08-18 の 5 本は全てこの形で始まっており、ユーザーから繰り返し指摘を受けた。現象・壊れ方・コードの断片を主語にすれば、読者の経験を断定せずに済み、書き出しも題材ごとに変わる。

判定は「この場面を経験していない読者は、この主題に出会わないのか」で行う。答えが No なら一般化しすぎである。

直し方は 2 段に分ける。まず主題に出会う条件そのものを、ドメインに依存しない言葉で書く。次に具体的なドメインの例を「〜が問題になる場面の代表は」で出す。後者の型は foreign-key・unique-constraint・soft-delete が既に使っている。

- 修正前: 開発者がこの決め方へ最初に触れるのは、注文の確定処理を書く時ではないでしょうか（2026-08-14、transaction-scope で指摘。「誰しもが注文処理を書くわけじゃないし、ここでしかトランザクション問題に触れるわけではない」）
- 修正後: この決め方が要るのは、1 つの要求で 2 つ以上の書き込みが必要になり、`BEGIN` と `COMMIT` をどこへ置くか選ぶ時です。＋ 範囲が問題になる場面の代表は、外部システムの呼び出しが途中に挟まる処理です

同じ文で、出会う対象と出会う場面が噛み合っているかも見る。状態や現象は、それが観測される場所でしか出会えない。コードを書いている時に出会えるのは、書く物（構文・設定項目・API）だけである。

- 修正前: 開発者がこの状態へ最初に出会うのは、複数の行を更新するコードを書いた時ではないでしょうか（2026-08-14、deadlock で指摘。コードを書いた時点ではまだ何も起きていない）
- 修正後: 開発者がこの名前を目にするのは、エラーログの中ではないでしょうか。PostgreSQL は `deadlock detected`、MySQL は `Deadlock found when trying to get lock; try restarting transaction` を返します

### 接続詞は、必要な所にだけ置く

前段の帰結が読み取りにくい所には「その結果、」を置く。逆に、因果が自明な所へ「そのため」を足すと冗長になる。

- 足した例: 「障害を検知できないクラスタは〜送り続けます。」→ 次の段落の頭に「その結果、」
- 削った例: 「そのため、実用的な障害検知は〜」→ 「実用的な障害検知は〜」
- 削った例: 「逆に、経路上のファイアウォールが〜」→ 「経路上のファイアウォールが〜」（対比が文脈から読める）

| 図の participant に `参加者 A の安定記憶` | `参加者 A のディスク` | 定着していない訳語を新造しない。stable storage の直訳は、読者が「何の事だろう」で止まる |
| その約束をクラッシュの後でも読み出せる安定記憶へ永続化する | クラッシュしても消えない場所へ約束を残す | 同じ物を記事の中で 2 つの名前で呼ばない。他の段落が「ディスク」で通しているなら揃える。名前を増やすより、効いている性質（消えない）を書く |
| この書き込みが、トランザクション全体の運命が決まる瞬間です | この書き込みで、トランザクション全体の結果が決まります | §11 比喩的な名詞を使わない。運命・宿命・命運は測れない |
| 誰にも裏切られずに確定を配れます | 勝手に中止した参加者が出る事を心配せずに確定を配れます | 機械を人格として描かない。何が起きないのかを動作で書く |
| 2F + 1 台の acceptor を〜（F は耐えたい故障の台数） | acceptor が何台まで同時に故障しても進めたいかを F として、2F + 1 台の〜 | §14 型5 記号の定義は式より前に置き、両方向に読めない言い方にする |

## 14. 丁寧さの型（読者への配慮）

nao の技術記事を読んで最初に感じるのは、読者を置き去りにしない書き方である。技術記事 156 本の実測でも、読者への配慮を表す語が繰り返し現れる（前提 61、注意 69、注意点 25、参考 77、かもしれません 24、してください 92、筈 19、でしょう 89）。

§11 の「事実は言い切る」と矛盾しない。言い切るのは仕組みの説明であり、丁寧さは「読者が今どこで詰まるか」を先回りして手当てする所に出る。断定と配慮は別の層にある。

ノートに持ち込むのは次の5つの型である。ブログの一人称語り（「私は〜で失敗しました」）は持ち込まない。

### 型 1: 前提を先に置く

読者と自分の立っている場所を揃えてから本題へ入る。前提が無いまま説明を始めると、読者は自分の環境と噛み合わない話を読み続ける事になる。

- 「前提として、エラーは `fmt.Errorf()` に `%w` フォーマットを適用する事によってラッピングできます」
- 「認識のレベル感を合わせるために、前提を以下に示します」
- 「本記事の手順は、CLI（Command Line Interface）を前提としています」

ノートでは、冒頭の定義の直後か、該当セクションの先頭に1〜2文で置く。「ここでは、ノードが故障で停止する場合だけを扱います。誤った値を返す故障（ビザンチン障害）は対象外です」のように、扱う範囲と扱わない範囲を明示する形が使いやすい。前提のためだけに `###` 見出しを立てる必要はない。

範囲の宣言は「ここでは」を必ず付ける。主語を落とすと、記事の範囲ではなく対象の性能として読まれる。

- 修正前: 「扱う故障は、ノードが停止する場合と、ネットワークが分断される場合の 2 つです」（クォーラムが対処できる故障の話に読める）
- 修正後: 「ここでは、ノードが停止する故障とネットワークが分断される故障を扱い、誤った値を返す故障（ビザンチン障害）は対象外とします」

なお「ここでは」は段落の先頭に置かない（→ §9）。定義の文へそのまま続ける。

「扱う範囲」という言い方は、ノートの説明範囲なのか、主題が扱えるデータや状況の範囲なのかが読み取れない（2026-08-10 ユーザー指摘）。宣言する側の範囲だと分かる語にする。範囲の持ち主も文の中に要る。「説明する範囲も決めておきます」だけでは、読者は「何の範囲だ」で止まる（2026-08-11 ユーザー指摘）。

宣言は 1 文へ畳む。「これから範囲を決めます」と予告してから範囲を書く 2 文の形は、前半が §26 の実況文にあたる（2026-08-18 ユーザー指摘）。

| | 例 |
|---|---|
| 修正前 | 扱う範囲も決めておきます。ここでは、1 台の DB が 1 本の索引を引く場合を扱い〜 |
| 修正前 | 本ノートで、説明する範囲も決めておきます。ここでは、1 台の DB が 1 本の索引を引く場合を扱い〜 |
| 修正後 | 本ノートでは、1 台の DB が 1 本の索引を引く場合を説明します |

「本ノートでは」で持ち主を与え、そのまま範囲の中身まで書き切る。前の版が 2 文だったのは、「ここでは」に受ける対象が無いという別の問題を「本ノートで、」で埋めていたためで、1 文へ畳めばその装置ごと要らなくなる。文中で範囲を狭める「ここでは」は今まで通り使える。

### 型を固定しない

2026-08-19 に本人から「毎回同じものを技術ノートに書くのは変だ」という指摘を受けた。原因は、このガイドが「本ノートでは、〜を扱い、〜は対象外とします」という 1 つの型を指定していた事である。実測では `〜を扱い、` がノート 49 本のうち 22 本にあり、本人の 54 万字には **0 件**だった（→ `voice_markers.md` 表 4）。

本人の宣言は、扱う事だけを 1 節で書き、動詞を場面で変える形である。

- 本記事では、電源投入から init プロセスが立ち上がるまでを記載します。
- 本記事では、この差異を説明します。
- 本記事では、ヒアドキュメントの書き方を比較します。
- 本記事では全文を示しません。

除外を並べる後半（「〜は対象外とします」）は本人の型に無い。扱わない範囲を書くのは、読者がそれを含むと誤解しそうな時だけにして、その時も別の文へ短く出す。動詞は「説明します」「比較します」「記載します」「示します」から、その回の中身に合う物を選ぶ。「扱います」で全部を通さない。

宣言そのものを毎回置く必要も無い。題名が扱う範囲を超えていて、読者が説明しない variant まで含めて読む恐れがある時に置く（→ `precision_claims.md` §49）。定義だけで範囲が分かるなら、書かずに本題へ入る。

この宣言はノート全体で 1 回だけにする。「本ノートでは、〜を扱います」を節ごとに繰り返さない。

前提の宣言も同じで、「本ノートで、前提を 2 つ置きます。」と予告せず、前提そのものを書く。「ノードは停止で落ちる場合だけを考え、誤った値を返す故障は対象外とします」で足りる。

この宣言が導入で 1 段落を占める場合、見出しを立てるなら `### 前提と説明の範囲` のように、範囲が誰の範囲かを見出しでも示す。

### 型 2: 読者が抱く疑問を先回りする

読者が「ここでこう思う筈だ」という所を言語化し、その場で答える。§12 の「読者を主語にする」を、より積極的に使う型である。

- 「勘の良い方は、『List 構造を next->next->… と辿れるけど、肝心のデータにアクセスできないのではないか』と考えたかもしれません。Linux Kernel は〜（後述）。そのため、List 構造ポインタからデータにアクセス可能です」
- 「コンパイラを自作した経験がある方は、『字句解析器や構文解析器を作るの大変だな』と考えるかもしれません」

疑問を投げっぱなしにせず、必ず直後で答える。答えが後のセクションになる場合は「（後述）」と行き先を示す。記事全体で 1〜3 回が目安である。

### 型 3: 注意点を独立させて示す

読者が踏みそうな所を、地の文へ埋めずに切り出す。

- 「追記時の注意点として、Kconfig 内の `endmenu` より前に追記しないと、`make menuconfig` 時に自作 Kernel モジュール用の設定が表示されません」
- 「AMD／Intel 環境の方は、`glXChooseVisual failed` エラーを上記の手順で解決できないため、ご注意ください」
- `#### 注意点：ファイルパスの区切り文字` のように `####` で立てる場合もある

ノートでは「欠点」「適さないケース」が既にその役割を持つので、見出しの乱立は避ける。仕組みの説明の中で読者が誤解しそうな1点だけ、「注意点として、〜」と地の文で立てる。

### 型 4: 一次情報へのリンクを本文に埋める

出典を示す事は、読者が自分で確かめられる状態を作る事である。記事末尾に「参考リンク」を並べるのではなく、その情報が必要になった位置へ埋める（§8 の「関連記事リストを作らない」と同じ理由）。

- 「より詳細な説明は、man ページ（`$ man 8 nologin` で表示するページ）に記載されています」
- 「型に応じて、どの変換指定文字を使用すべきか迷った場合は、[公式ドキュメントに逆引きが存在](https://www.kernel.org/doc/html/latest/core-api/printk-formats.html)します」
- 「この辺りの話題は、「[記事タイトル](URL)」に詳しく書かれています」

ノートでは、アルゴリズムの原論文・RFC・公式ドキュメントが対象になる。断定した仕様の根拠がある所に置くと、事実確認の査読（Step 6.7）とも噛み合う。1本あたり 1〜4 個が目安である。

リンクを張る範囲は、引用した英語そのもの、または出典の名前に限る（2026-08-14 ユーザー指摘。それ以前は引用文と述語までを 1 つのリンクに含める規則だったが、下線が長くなりすぎるため改めた）。リンクは下線として描画されるので、範囲を広げるほど本文が下線で埋まる。

英語を引用する場合は、`「」` の内側だけをリンクにする。訳文と述語はリンクの外へ出す。

| 修正前 | 修正後 |
|---|---|
| [「The default size of an index page is 16KB」（索引ページの既定の大きさは 16KB）と書いています](URL) | 「[The default size of an index page is 16KB](URL)」（索引ページの既定の大きさは 16KB）と書いています |

英語の引用が無く日本語だけで書く場合は、出典の名前をリンクにして、主張は地の文へ出す。文中に出典名が無ければ補う。

| 修正前 | 修正後 |
|---|---|
| PostgreSQL のドキュメントは、[葉が表の行を指す項目を持つと説明しています](URL) | [PostgreSQL のドキュメント](URL)は、葉が表の行を指す項目を持つと説明しています |
| [MySQL の `innodb_lock_wait_timeout` は既定が 50 秒です](URL) | [MySQL](URL) の `innodb_lock_wait_timeout` は既定が 50 秒です |
| [検出して犠牲に選ばれたトランザクションは、全体が巻き戻されます](URL) | [InnoDB のドキュメント](URL)によれば、検出して犠牲に選ばれたトランザクションは、全体が巻き戻されます |

出典名として使えるのは「PostgreSQL のドキュメント」「同じページ」「白書」「BIP 125」「RFC 6750」「Evans 氏の DDD Reference」のような、それだけで何を指すか分かる語である。主張の主語をそのまま出典名だと思って囲まない（`[policy が、〜と説明しています](URL)` の「policy」は出典ではない）。

リンクテキストが「書いています」「求めています」のような動詞 1 語だけになる形は、改定後も避ける。何の出典か分からないためである。

同じ URL を隣接する文で 2 回リンクしない。2 文目は「同じドキュメント」「同じページ」で受けて、リンクは 1 回だけ張る。

貼る前に必ず取得して中身を見る。記憶で URL を組み立てると、実在しないページや別のページを指す。HTTP 200 が返っても中身が違う事があるので、状態コードだけで判断しない。

引用の近くにあるリンクが、その引用の出典とは限らない。リンク先の本文を検索して、引用が実在する事を確認する。含まれないなら出典を別に書く。章番号やページのような位置情報も、原典で確認してから書く。

- 指摘された例: 「[Evans の DDD Reference](URL) は〜と定義しています」の 2 段落後に「Evans は、大規模なシステムでドメインモデルを完全に統一する事は〜と書いています」と続けた。後者の一文は Reference には無く、書籍『Domain-Driven Design』の記述だった。リンクが近くにあるだけで、読者は Reference が出典だと読む
- 対応: 「Evans は書籍『Domain-Driven Design』（2003 年）の第 14 章で〜と書いています」と、出典を文の中で名指しした。章番号は原典を取得して確認した

```bash
curl -s -o /dev/null -w "%{http_code} %{content_type}\n" -L "<URL>" --max-time 20
```

論文へリンクする場合、著者名と発表年を本文に書いてからリンクする。「原論文」「前述の論文」のような指示表現は、指す対象が本文中で既に特定されているときだけ使う。特定されていない指示表現は、読者にとって参照先の無い代名詞になる。

「ここでの〜」も同じ扱いになる。この語は直前に出した語を受けて範囲を限定する形なので、受ける対象が無いと読者は探しに戻る事になる。限定したい対象が本文でまだ特定されていないなら、指示語を外して普通の文で書く。

他の節を「前の節の〜」「先ほどの〜」で参照するのも同じ問題を起こす。読者は該当箇所を思い出すか、戻って読み直す事になる。参照するなら、その内容を短く言い直して名前で呼ぶ。

節を数えて指す「最後から 2 つ目の節」「3 つ目の節」も同じ理由で使わない。読者は見出しを数え直す事になり、節を足した時に書き手も直し忘れる。節は見出しの文字列でそのまま呼ぶ（2026-08-10、B-Tree ノートでの著者の指定。実際その時点で 11 節中の 7 番目を指しており、記述そのものが古くなっていた）。

- 修正前: 「値をどこへ置くかで名前が分かれる事情は、最後から 2 つ目の節で扱います」
- 修正後: 「B-Tree と B+tree の違いは「葉に値を集める B+tree」の節で扱います」

同時に、何を扱うのかも読者の語彙で書く。「値をどこへ置くかで名前が分かれる事情」は書き手の要約で、読者が知りたいのは「B-Tree と B+tree の違い」である。

- 修正前: 「〜を見込んだ待ち時間で、前の節のマージンの実例になっています」
- 修正後: 「〜を見込んだ待ち時間は、Grantor が期限より少し遅く次の相手へ貸すというマージンの実例になっています」

「後述の fencing token」のように、対象を名前で呼んでいる前方参照は問題ない。読者は何を待てばよいかが分かる。

「以下では」も指す先が曖昧になりやすい。直後に来るのが図なのか、節全体なのかが読者には分からないためである。図を指すなら「下図では」と書き、節全体を指すなら指示語を外して目的をそのまま書く。

ノートの残り全体に掛かる宣言なら「以降の」を使う。「以下の図と説明は〜」と書くと、直後の図 1 枚だけの話に読める（2026-08-10、B-Tree ノートで指摘）。

- 修正前: 「以下の図と説明は、値を葉へ集めた B+tree という形で描きます」（実際にはノートの最後までこの形で通していた）
- 修正後: 「以降の図と説明は、値を葉へ集めた B+tree という形で描きます」

- 修正前: 「ここでの期限の無いロックは、その内蔵が無い場合に何が起きるかを見るための想定です」
- 修正案: 「以下では、その仕組みを持たないロックから出発して、期限が何を解決しているのかを見ていきます」（「以下」が図か節かで詰まる）
- 修正後: 「その仕組みを持たないロックを出発点に置くと、期限が何を解決しているのかが見えます」

- 修正前: 「当てはめる分布は実装によって違い、原論文と Akka は正規分布、Cassandra は指数分布を使います」（それまで論文に触れていない）
- 修正後: 「Phi Accrual Failure Detector は、Hayashibara らが 2004 年に発表した論文「〜」で提案された方式です」と先に置いてから、「上記の論文と Akka は正規分布、〜」

### 型 5: 初出の略語と固有名詞に、特徴が掴める説明を付ける

読者が詰まる原因で最も多いのが、説明されないまま流れていく略語である。書き手には見慣れた語なので、抜けても気付けない。ノートは初見の読者が引く場所なので、ブログ記事より丁寧に補う。

段階は3つある。

1. 略語は初出で展開する。「GC（Garbage Collection、ガベージコレクション）」「NTP（Network Time Protocol）」「WAL（Write-Ahead Log、先行書き込みログ）」
2. 展開しても意味が取れない語は、1文で「何をするものか」を添える。「GC（Garbage Collection、ガベージコレクション）は、使われなくなったメモリを自動で回収する処理です。回収中はプログラムの実行が数百ミリ秒から数秒止まる事があります」
3. TCP や HTTP のように展開しても情報が増えない有名な語でも、そのノートの主張がその性質に寄りかかっているなら、寄りかかっている性質だけを1文で書く。「TCP は接続を保ったまま通信する規約です。接続の相手が停止しても、次に送信を試みるまで切断に気付けません」

判定基準は「その語を知らない読者が、この段落の主張を追えるか」である。追えるなら展開だけで足りる。追えないなら、その段落で効いている性質を書く。

カタカナの専門用語（デッドロック、ソケット、シャード、レプリカ）も同じ扱いになる。英字の略語だけを見て安心しない。

箇条書きの中で初めて出す略語は、展開を入れると 1 行に収まらなくなる。項目は短いまま残し、リストの直後に 2〜3 文で説明する段落を置く。

- 修正前: 「- 分断中も両側で書き込みを受け付けたいシステム。後から併合できるデータ型（CRDT）を検討する」（CRDT が何かは分からないまま終わる）
- 修正後: 項目は「CRDT のような、後から併合できるデータ型を検討する」とし、リストの後に「CRDT（Conflict-free Replicated Data Type）とは、複数のノードが独立に更新しても、後から併合すれば必ず同じ結果へ収束するように作ったデータ型です。〜」を置いた

#### 1 文字の記号は、使う場所ごとに意味を添え直す

`N` `W` `R` のように 1 文字で定義した記号は、定義した段落から離れるほど読者の負荷になる。節をまたいで使うなら、その節の初出で「W は書き込みに必要な応答数」と短く添え直す。表の見出しに裸で置くのも避け、意味と記号を並べる。

- 修正前: 表の見出しが `| W | R | W + R > N | W > N / 2 | 性質 |`
- 修正後: `| 書き込み W | 読み取り R | 読み書きが重なる W + R > N | 書き込み同士が重なる W > N / 2 | 性質 |`

数値のセルにも単位を付ける（`1` ではなく `1 台`）。条件式を見出しに置く場合は、その式が何を意味するのかを同じセルに書く。

定義は、その記号を使った式より前に置く。文末の括弧へ回すと、読者は `2F + 1 台` を意味の分からないまま読み、括弧まで来て戻る事になる（2026-08-10 の著者の指定）。

- 修正前: 「2F + 1 台の acceptor を使った Paxos で複製し、F + 1 台以上が通信できていれば決定まで進められます（F は耐えたい故障の台数）」
- 修正後: 「acceptor が何台まで同時に故障しても進めたいかを F として、2F + 1 台の acceptor を使った Paxos で複製します。1 台の故障まで許すなら F = 1 で、acceptor は 3 台になります」

定義の言い方は、両方向に読めないかを確かめる。「耐えたい故障の台数を F として」は、F 台が故障する側なのか、故障に耐えて動き続ける側なのかが決まらない（同日の著者の指定）。増えると何が増えるのかまで書き、具体値を 1 つ添えると、読者は自分で検算できる。

逆に、説明を足すほどでもなく、本文の理解にも効いていない語は、書かずに済ませる方が読みやすい（§12）。

#### 定義を後ろへ回さない

新しい語を出したら、その場で「〜とは、〜です」と定義する。動機や背景を先に置くと、読者は「これは何だろう」と抱えたまま数段落を読む事になる。理由が知りたくなるのは、それが何かを知った後である。

- 修正前: 見出し `#### fencing token` → 仮定が破れる話を 5 文 → 「この用途で使う番号が fencing token です」
- 修正後: 見出し `#### fencing token` → 「fencing token とは、権利を貸すたびに大きくなる番号で、保護対象が古い権利からの操作を拒否するために使います」→ 必要になる理由

見出しに語を置いた場合は特に効く。読者は見出しを読んだ時点で定義を期待しているので、そこから遠いほど負荷が上がる。

設定項目を出す時も同じで、既定値より先に「その設定が何を決めるのか」を書く。真偽値は特に危なく、何の真偽なのかを知らないまま true と言われても読者は判断できない。

- 修正前: 「Amazon ECS のコンテナは `essential` の既定が true です。公式ドキュメントは、〜と書いています。sidecar の停止を切り離すには false にします」
- 修正後: 「Amazon ECS には、コンテナの停止を実行単位の全体へ波及させるかどうかを決める `essential` という設定があります。公式ドキュメントは、〜と書いています。既定は true なので、〜には false にします」

自分で導入した抽象語にも同じ規則が掛かる。特定の製品名を避けて「実行基盤」「実行単位」のような語を作った場合、その語は読者にとって完全な新語である。製品名を出さない事と、定義を書かない事は別である。

- 指摘された例: 「実行基盤」を定義せずに 9 回使い、読者が「正体不明の何かが良きに計らってくれる話」として読んだ
- 対応: 冒頭で「コンテナの配置とライフサイクルを管理する基盤は、ここでは実行基盤と呼びます。Kubernetes や Amazon ECS がこれにあたります」と 2 文で定義した

#### くどくしない

読者には、その分野を長くやっている人も含まれる。既知の語を延々と教えられる文章は、その人にとって読み飛ばす対象になる。丁寧さと冗長さは別物なので、次の3点で抑える。

第一に、説明のための独立した文を足すのは、その性質が本文の主張の前提になっている時だけにする。それ以外は括弧内の展開で止める。理想は、説明の文を足さずに、必要な性質が主張と同じ文の中に現れている形である。

- くどい: 「GC（Garbage Collection、ガベージコレクション）とは、使われなくなったメモリ領域を自動的に見つけて解放する仕組みです。これによって開発者はメモリ管理を意識せずに済みます。ただし、実行中はプログラムが停止します。そのため、〜」
- 適切: 「GC（Garbage Collection）による停止で、プロセスが数秒応答しなくなる事があります」

第二に、同じ語を2度説明しない。初出で処理し、以降は素の語で通す。

第三に、噛み砕きすぎない。「メモリのお掃除係」「交通整理をする人」のような比喩は、専門家には幼稚に映り、初学者にも正確な像を与えない（§3 の比喩の方針と同じ）。読者を、その語をまだ知らないだけの技術者として扱う。

### 型 6: 読者の状況の違いに配慮する

全員が同じ環境・同じ知識で読んでいるとは考えない。

- 「Vala 言語に興味がある方は、Ubuntu、Fedora、Arch Linux あたりを使うと良いかもしれません」
- 「PC ゲームをプレイする場合は NVIDIA を使う方が多いと思いますが、グラフィックボードは AMD や Intel も存在します」

ノートでは、条件によって結論が変わる所で使う。「拠点が1箇所に収まっている構成では〜で足りますが、拠点をまたぐ場合は〜を検討してください」のように、読者が自分の状況へ当てはめられる形にする。

## 15. 皮肉を書かない（批判の作法）

技術ノートは比較と評価を書く場所なので、書き方を誤ると対象を貶す文章になる。nao の記事は、技術を批判するときも対象への敬意を先に置く。

### 批判の前に、対象の良い点を認める

- 「大前提として、Bash は良い言語であり、私は Bash が好きです。主要な Linux ディストリビューションにインストールされていますし、POSIX 互換を意識して書けば移植時の修正箇所が減ります」（この後に Bash の限界の話が続く）

ノートでは一人称を使わないので、「何を優先した結果その欠点があるのか」を書く形に置き換える。欠点は設計判断の帰結であって、設計者の怠慢ではない。

- 修正前: 「二値でしか扱えないため、一時的な遅延で簡単に誤検知します」
- 修正後: 「実装の小ささを優先した結果、生死の二値でしか扱えません。そのため、一時的な遅延が誤検知になります」

### 「とは言え」で自分の主張に留保を付ける

自分の書いた評価を自分で引き戻す型で、読者を断定で押し切らない効果がある。

- 「Brand 拡張仕様は NDA があり、公開できません。とは言え、2026 年の今は LLM があるので、spec ファイルの骨組みを簡単に作れる筈です」

### 書かないもの

| 避ける書き方 | 理由・代替 |
|---|---|
| 反語で見下す（「〜と思ったら大間違いです」「〜で済むと考えるのは早計です」） | 読者を試す書き方になる。「〜は〜のため、この方法では解決できません」と事実で書く |
| 後知恵の断罪（「最初からこうしておけば良かった話です」） | 当時の制約を知らずに書く事になる。設計の背景を書くか、触れない |
| 突き放し（「これ以外に手がありません」「使う理由はありません」） | 理由を添えて言い切る。「落ちたノードは自分の停止を報告できないため、不在を手がかりにする以外の方法がありません」 |
| 嘲り・レッテル（「素朴な実装」「雑な設計」「時代遅れ」） | 「単純な実装」「最小限の実装」のように中立な語へ置き換える |
| 他技術の一方的な否定（「〇〇は使い物になりません」） | 適用条件の違いとして書く。「〇〇は〜の前提が置ける場面では十分です」 |
| 読者の理解力への当てこすり（「言うまでもありませんが」「常識ですが」） | 削除する。知らない読者に対して何の情報も足していない |

判定の目安は「その技術を作った人が読んでも、事実の指摘として受け取れるか」である。受け取れないなら、評価ではなく感情が混ざっている。

## 16. 主語と助詞、文の切り方

このセクションの「は」と「が」の使い分けは、主語を追える状態に保つための規則である。

一方、接続の「が」と書き出しの「また、」の禁止は 2026-08-19 に解除した。実測で本人が接続の「が」を 1 万字あたり 4.2 件、書き出しの「また、」を 1 万文あたり 98 件使う一方、ノートは両方 0 件だった。禁止が本人の文体から遠ざける方向に働いていたので、実測へ合わせている。

### 主語を明確にする

述語に対して誰が主語なのかを、読者が必ず読み取れるようにする。分散システムやアーキテクチャの説明は登場人物が多く、主語を落とすと「誰がやるのか」が消える。

- 修正前: 「閾値を超えると故障とみなします」
- 修正後: 「閾値を超えると、監視側はそのノードを故障とみなします」

### 「は」は新規、「が」は継続

新しく持ち出す主題には「は」を付け、既に出ている主題を受け継ぐときは「が」を使う。

```
Lease は、期限付きで権利を与える仕組みです。その Lease が切れると、
旧リーダーは書き込みをやめます。
```

1文目で Lease を新しく持ち出しているので「は」、2文目は同じ Lease を受けているので「が」になる。この使い分けが崩れると、読者は「今どれの話をしているのか」を毎文で組み立て直す事になる。

### 接続の「が」は、意味が決まる時だけ使う

本人は「〜ですが、」「〜ますが、」を 1 万字あたり 4.2 件使う（ノートは 0 件）。禁止しない。

ただし、この「が」は逆接とも単純な接続とも取れるので、どちらの意味か文脈で決まらない所では使わない。決まらないなら文を切って、「しかし」「ただし」「一方で」で受ける。

- 修正前: 「pull 型は応答性まで確認できますが、対象一覧の管理が必要です」
- 修正後: 「pull 型は応答性まで確認できます。ただし、対象一覧の管理が必要です」

### 書き出しの「また、」は使ってよい

本人は文や段落の頭で 1 万文あたり 98 件使う（ノートは 0 件）。2026-08-19 に禁止を解除した。

並列する内容が 3 つ以上あるなら、「また、」で繋がずに箇条書きか表へ移す。そこは量の問題であって、語の問題ではない。

### 「〜ため、」で繋ぐ前に、切れないか検討する

「〜ため、」は原因と結果を1文へ押し込む。1文が長くなるなら切って、2文目を「そのため、」で受ける。

- 修正前: 「壁時計は NTP の補正で進んだり巻き戻ったりするため、そのまま差分を取ると故障判定が早まったり遅れたりします」
- 修正後: 「壁時計は NTP の補正で進んだり巻き戻ったりします。そのまま差分を取ると、故障判定が早まったり遅れたりします」

判定は、「ため」の前後がそれぞれ独立した主張になっているかで決める。独立しているなら切る。前半が後半の条件を述べているだけなら、繋いだままでよい。

## 17. 指示語で文を始めない、修飾節を読点で割らない

2026-08-06 に本人から受けた指摘。どちらも `scripts/style_check.sh` では検出しにくいので、書き終えたら目視で当てる。

### 「これは」で文を始めない

直前の文を受け直す「これは」「それは」「この点は」は、読者を前の文へ戻らせる。受けたい対象を主語として立て直せば、指示語は要らなくなる。

- 修正前: 「これは Aggregate で見た、〜経路と同じ形です」
- 修正後: 「集約ルートを迂回して明細を書き換える経路は、Aggregate でも扱いました」

判定は「その『これ』が指す物を名前で書けるか」で行う。書けるなら書く。§11 の「抽象名詞と指示語で対象をぼかさない」と同じ規則が、文頭の指示語にも掛かる。

### 連体修飾節の中に読点を打たない

「〜で見た、〜経路」のように、名詞へ掛かる修飾節の途中で読点を打たない。読者は読点で文が切れると予想して読み進め、直後に名詞が来て読み直す事になる。

- 修正前: 「Aggregate で見た、集約ルートを迂回して明細を書き換える経路と同じ形です」
- 修正後: 「集約ルートを迂回して明細を書き換える経路は、Aggregate でも扱いました」

修飾節が長くて読みにくいなら、読点で割らずに文を 2 つへ分ける。読点は、主語の後ろか、節と節の境目にだけ置く。

## 18. 先送りで文を埋めない

2026-08-07 に本人から受けた指摘。「後で扱います」「ここでは〜だけを見てください」「以下の主題になります」で段落を埋めると、読者は待たされるだけで何も受け取れない。ノートは後から引くリファレンスなので、必要な箇所を拾い読みする読者にとって、先送りの案内は空白と同じである。

- 修正前: 「点線の配送が何を経由するのかは後で扱うので、ここでは 2 つのトランザクションが分かれている事だけを見てください。この分割が何を解決するのかが、以下の主題になります」
- 修正後: 「点線の配送は、同じプロセスの中でハンドラを呼ぶか、メッセージブローカーを挟むかのどちらかです。トランザクションを分けた事で、注文の確定は在庫の混雑から切り離され、代わりに 2 つの状態がずれている時間が生まれます」

判定は「その文を消した時、読者が失う情報があるか」で行う。無いなら消す。図の直後の段落で起きやすい。図に描いた要素へ触れないまま「後で扱う」と書く形が典型で、触れるべき要素があるなら、その場で 1 文で答える。

先送りが許されるのは、答えを 1 文で書いた上で、展開する場所を添える場合に限る。

- 許される: 「Leader から Follower へ戻る経路は、自分より新しい任期を検知した時に通ります。分断から復帰した旧 Leader がここを通るので、「古い Leader を締め出す」で改めて扱います」
- 許されない: 「Leader から Follower へ戻る経路は、後の「古い Leader を締め出す」で扱います」

節の冒頭で「本節では〜を説明します」と予告するのも同じ理由で書かない（→ §2 見出し直下のリード文）。

## 19. 出典にページ番号を書かない

2026-08-07 に本人から受けた指摘。書籍のページ番号は、後から正しさを確かめるのに現物が要る。手元に無い読者は検証できず、書き手も改版でずれた事に気付けない。ページ番号を落としても、書名と引用文があれば出典として成立する。

- 修正前: 「Evans の書籍『Domain-Driven Design』128 ページから「〜」という一文も引いています」
- 修正後: 「Evans の書籍『Domain-Driven Design』から「〜」という一文も引いています」

`p.128` `pp.30-35` のような表記も同じ扱いにする。

論文の節番号（「Raft 論文 5.4 節」）と RFC のセクション番号は書いてよい。本文が公開されていて、リンク先を開けば誰でもその場で確かめられるためである。判定の軸はページか節かではなく、読者がリンクだけで検証を完了できるかにある。

引用の帰属そのものは省かない。どの文献から引いたかを書かずに引用だけ置くと、出典が無い記述になる（→ §14 型4）。

## 20. 引用に言い換えを足す時は、原典の続きまで読む

2026-08-07 に本人から受けた指摘。読者が引用の中の語で詰まった時、その語を言い換えて補うのは正しい対処である。危ないのは、言い換えが原典の主張から離れて別の概念の説明になる場合で、引用文そのものは正確なまま記事が誤る。文体チェックも、引用が実在するかの確認も、この誤りを検出しない。

- 元の引用: 「ドメインの活動に関する情報を一つ一つ区切られた出来事の連なりとしてモデル化し」
- 誤った言い換え: 「注文の現在の状態を 1 つの値として持つのではなく、確定した・出荷した・返品されたという出来事を起きた順に並べて持つ形」
- 正しい言い換え: 「業務上意味のある出来事を 1 件ずつ独立したドメインオブジェクトとして明示する形」

誤った方は Event Sourcing の説明になっている。原典が言っているのは、ドメインの出来事を明示的にモデル化せよという事で、現在の状態を捨ててイベントだけを保存せよという指示ではない。

要約でも同じ事が起きる。英語の原典を日本語へ移す時に法助動詞 (may, can) を落とすと、可能性の記述が断定へ変わる。2026-08-08 の Anticorruption Layer ノートで実際に外した例を挙げる。

- 原文: 「Yet the integration may be very valuable or even required for the downstream project.」
- 誤り: 「統合そのものは下流にとって価値があり、必要ですらあるので、統合をやめる選択は残りません」
- 修正後: 「それでも統合は下流にとって価値を持つ事があり、必要とされる事すらあります」

誤りの方は、原典が別のパターン (Separate Ways) として併置している「統合しない」という選択を否定する文になっていた。法助動詞を落とすと、原典が残した選択肢まで消える。

手順は 3 つある。第一に、言い換えの根拠を、引用した一文ではなくその前後から取る。原典は引用箇所の後ろで必ず何かを補足しており、そこに範囲を狭める記述がある。第二に、書いた言い換えが、その分野の別の概念の定義になっていないかを確かめる。隣接する概念の名前を挙げ、その定義と読み比べる。第三に、同じ概念へ触れた記事の中の他の箇所と突き合わせる。上の例は、記事の末尾に置いた「Domain Event を使う事は、Event Sourcing を採用する事を意味しません」と正面から矛盾していた。

言い換えを足した箇所は、査読で裏取りする対象へ必ず入れる（→ `review_prompts.md` 観点 6）。読者に「分からない」と言われて補った箇所ほど、書き手は良かれと思って踏み込むため、外しやすい。

## 21. 製品の解説ではなく、パターンを説明する

2026-08-08 に本人から受けた指摘。Sidecar のような設計パターンを扱うノートで、説明に使った実装（Kubernetes）の API と設定が本文の主役になっていた。読者は Sidecar を知りたくて開いており、その実装を使っていない読者にとっては前提知識が増えただけになる。

判定は「その実装を使っていない読者が、このノートで主題を理解できるか」で行う。理解できないなら、実装の説明が主題の説明を押しのけている。

### 実装を出してよい位置

パターンを扱うノートでは、実装は次の 3 つの位置にだけ置く。

| 位置 | 書く事 | 分量 |
|---|---|---|
| 冒頭の抽象語の定義 | 自分で作った語が、どの製品に対応するのか | 1 文 |
| 条件が付く性質の反例 | その性質が成り立たない実装を 1 つ | 2〜4 文。引用と出典リンクを添える |
| 節の締め | 実装ごとに表し方が違う事と、詳細をドキュメントへ譲る宣言 | 1〜2 文 |

API 名・設定ファイルの書き方・バージョンごとの差は、この 3 つのどれにも入らない。別のノートへ切り出す。

### 抽象化した時に増える 3 つの穴

実装固有の語を抜いた後は、抜いた場所に穴が空く。次の 3 つは実際に指摘された。

第一に、代わりに置いた抽象語が定義されない（→ §14 型5）。製品名を避ける事と、定義を書かない事は別である。

第二に、抽象化した定義と、後から書いた但し書きが矛盾する。「一緒に起動・停止される」と定義した後で「ライフサイクルはコンテナごとに分かれる」と書くと、読者はどちらが正しいのか決められない。抽象化の後に全文を通しで読み、定義と但し書きを突き合わせる。

第三に、抽象度が 1 箇所だけ深くなる。Kubernetes を追い出した席へ Linux カーネルが座る形で、Sidecar ノートでは cgroup の階層と OOM Killer の victim selection まで踏み込んでいた。主題の理解に要らない層は、削っても本文が成立するかで判定する。成立するなら削る。

### 原典の分類を、書き手の都合で親子関係に変えない

同じ論文が並列に挙げたパターンを、片方を総称・残りを下位分類として書き直すと、原典に無い階層を原典の主張として配る事になる。2026-08-08 の 3 ノートは「Sidecar は総称で、Ambassador と Adapter は対象を絞った 2 つ」と書いていたが、ブログは 3 つを Example #1〜#3 として、論文は 4.1〜4.3 節として並べているだけだった。

現場の呼び方が原典とずれている場合は、両方を書いて食い違いとして示す。どちらかへ寄せて 1 つの説明にまとめない。

- 原典では 3 つが並列で、上下の関係は付いていない
- 現在は同居する補助コンテナ全般を sidecar と呼ぶ用法も広まっている
- どちらの意味かは文脈で判断する

### 姉妹ノートを読まないと意味が取れない文を書かない

シリーズで複数のノートを書くと、まだ説明していない姉妹パターンの名前で判断基準を書いてしまう。読者はそのノートから読み始めるので、前方参照は疑問を増やすだけになる。

- 修正前: `仕組み` の途中で「[Ambassador](../ambassador/) との切り分けは通信の向きではなくアプリケーションの役割で決まります」（Ambassador はまだ引用の中に 1 度出ただけ）
- 修正後: 「要求を受け取る向きは監視の例と逆になります。それでも、アプリケーションがサーバとして外へ見せる形を揃えている点は変わりません」

比較の節は立てない。特に `### 適さないケース` の後ろに `### 〜との違い` を足さない（→ `SKILL.md` Step 4。結論を書いたら話を伸ばさない）。区別が主題の理解に必要なら、相手が初めて話に出る段落の中で、その段落だけで完結する 1〜2 文にする。

## 22. 主題が一般名詞のときは、その名詞を単独で使わない
23. 英語を引用したら、直後に日本語訳を括弧で置く
24. 用語は、ノートをまたいで 1 つに決める

2026-08-08 に本人から受けた指摘。Anticorruption Layer のノートで、主題を「層」と略して 30 回近く書いていた。読者は「層」を見るたびに、ACL の事なのか、DTO の説明に出てくるアプリケーションの層の事なのか、引用の中の facade / adapter layer の事なのかを判定する事になる。「一瞬どれのことかを考えてしまう」という指摘が、図を受ける文で 2 回続けて出た。

主題の名前が「層」「境界」「単位」「基盤」「経路」のような一般名詞を含む場合、その名詞を単独で主題の代わりに使わない。記事の中で通す呼び名を 1 つ決め、次の 3 箇所では必ずその呼び名で書く。

| 位置 | 単独の一般名詞では読めない理由 |
|---|---|
| 見出し | 目次には見出しだけが文脈なしで並ぶ。「層を置く場所」では何の層か決まらない |
| 節・段落の 1 文目 | 直前に受ける対象が無い。読者はそこで主題を組み立て直す |
| 図の橋渡し文と、図を受ける文 | 図の中のどれを指すのかを、読者が図と本文の間で往復して探す |

段落の途中で、直前の文が既に呼び名を出しているところは一般名詞のままでよい。同じ略語が 1 段落に 3 回並ぶ方が読みにくい。判定は「その文だけを取り出した時、何を指すのかが決まるか」で行う。

### 呼び名は、実際の使用回数で決める

候補が複数ある時は、本文で何回使われているかを数えてから決める。ACL のノートは ACL が 20 回、訳語の「腐敗防止層」が 1 回、英語の `Anticorruption Layer` が 7 回だった。ここで見出しに「腐敗防止層」を出すと、同じものに 3 つ目の呼び名が付く。訳語は冒頭で 1 度示すだけにして、本文は使用回数の多い呼び名で通す。

### 別の意味で使う時は、必ず修飾を付ける

同じ名詞を別の意味で使う箇所には修飾語を付ける。付けられないなら、その語を使わずに書き直す。

| 修正前 | 修正後 |
|---|---|
| DTO（Data Transfer Object、層の間でデータを運ぶためのオブジェクト） | DTO（Data Transfer Object、データを受け渡すためのオブジェクト） |
| 2 つは同じ層に並ぶ概念ではありません | 2 つは同じ種類の概念ではありません |
| ACL は、その防御的な位置に置く層です | 統制や意思疎通が弱い関係では、ACL はより防御的な役割を持ちます |

修飾が付いていれば残してよい。ACL のノートで残したのは「腐敗防止層」「隔離層」「翻訳層」と、引用の中の「facade または adapter の層」だけである。前の 3 つは原典の isolating layer / translation layer に対応する訳語で、単独の「層」とは別の語として読める。

書き上げたら `grep -o "[^。]\{0,12\}<一般名詞>" <ファイル>` で全用例を出し、1 つずつ修飾の有無を確認する。

### 定義した語を、別の節で略さない

2026-09-04 の nonce で受けた指摘。冒頭の節で「鍵ストリーム（平文と同じ長さの疑似乱数列）」と定義し、2 つ先の節で「鍵を知らない相手が nonce を知っても列は作れません」と書いた。本人から「列って何」という指摘を受けた。

2026-09-06 の hash-function でも同じ型を踏んだ。padding の節で「32 bit のまとまりを 1 語（word）として、16 語に分けて読みます」と定義し、以降の 3 節で「語ごとに足す」「64 ラウンドが使う語 `W_t`」「4 つの語」「ある語の違い」と書き続けて、本人から「語は word？」という指摘を受けた。「語」は FIPS 180-4 の word の訳語だが、1 文字の漢字なので節を離れると「用語」「単語」と同じ字面に埋もれる。直し方は、本文と図の全てを `word` に統一し、括弧の併記を「1 つの word（語）」の 1 箇所だけに残す事だった。

読者が略語を解ける範囲は、その語を定義した文が視界に入っている間だけである。節をまたぐと、直前の文も図も別の物に変わっているので、解く手掛かりが残らない。

節をまたいで使ってよい短い形は、次の 2 つだけである。

- 初出で展開を書いた英字の略語（AAD・IV・ACL）。展開せずに使い始めるのは別の違反である
- その分野で指す先が 1 つに決まるカタカナの短縮（「認証タグ」→「タグ」）

逆に、1 文字の漢字へ縮めた形（列・層・値・式・鍵・数・語）は、節をまたいで使わない。同じ節の中で、直前の文が呼び名を出している場合だけ許す。

訳語がこの形になる場合は、和語を捨てて原語の綴りで通す方が早い。「語」「木」「鍵」のような 1 文字の訳語は、`word`・`tree`・`key` と書けば読者が迷わず、本人も技術用語を英語のまま書く（→ `voice_samples.md`）。括弧の併記は初出の 1 箇所だけに置く。

特に踏みやすいのは、定義の括弧の中の語を本体の代わりに使う形である。「鍵ストリーム（平文と同じ長さの疑似乱数列）」の括弧は言い換えであって呼び名ではないので、「列」は最初から呼び名になっていない。略語を作るなら、括弧からではなく本体から作り、初出で「以降は〜と書きます」と宣言してノート全体で 1 つに統一する（→ §24）。

| 修正前 | 修正後 |
|---|---|
| 鍵を知らない相手が nonce を知っても列は作れません | 鍵ストリームを作るには鍵と nonce の両方が必要なので、nonce を手に入れただけの相手には再現できません |
| nonce が同じなら平文が違っても同じ列になります | nonce が同じなら平文が違っても同じ鍵ストリームが出ます |

機械で拾えるのは、括弧で原語と対にして定義した場合だけである。`scripts/name_drift.py` が `語（word）`・`word（語）` の形を起点に、1 文字の漢字の呼び名が定義した h3 の外で使われていないかを見る。既存ノート 55 本では誤検出が 0 件で、上の hash-function の初稿だけが引っ掛かる。`style_check.sh` から呼ばれるので、単体で走らせる必要は無い。

括弧の併記が無い場合は目で行う。語尾の一致だけを頼りにする方法は使えない。「3 文字以上の語の末尾 1 文字が、別の節で単独で使われている箇所」を既存ノート 54 本へ当てると 107 件出て、そのほとんどが「設定項目」の「項目」、「参照先」の「先」、「注意点」の「点」のような普通の形式名詞だった。閾値では本物と区別できない。

書き上げたら、節をまたいで出てくる 1〜2 文字の語を拾い、その 1 文だけを取り出して何を指すかが決まるかを見る。決まらないなら呼び名で書き直す。

### 綴りが割れる名前は、原典に合わせて 1 つに決める

同じパターンの綴りが文献によって違う事がある。Evans の DDD Reference は 3 箇所とも `Anticorruption`、Microsoft の Azure Architecture Center は `Anti-Corruption Layer` と書く。本文は原典側の綴りで通し、別の綴りがある事を冒頭で 1 文だけ添える。ディレクトリ名は、検索で打たれやすい方に寄せてよい。

## 23. 英語を引用したら、直後に日本語訳を括弧で置く

2026-08-11 に本人から受けた指摘。ノートは日本語で読まれるので、原典の英文をそのまま置くと、そこだけ読者が翻訳を担う事になる。公式ドキュメント・RFC・論文から英文を引用したら、閉じ括弧の直後に全角括弧で訳を置く。

この節が決めるのは、残すと決めた引用の書き方である。そもそも引用を置くかどうかは §25 で決める。裏付けだけが目的の引用は、英語を置かずに日本語で書いて出典名へリンクを張る。

- 書式: `「原文の英語」（日本語訳）と書いています`
- リンクの中に引用を含める書き方をしている場合は、訳もリンクの中へ入れる（`[「...」（...）と書いています](URL)`）

訳を付けない例外は次の 3 つに限る。

- 論文・記事・仕様の題名（「Consensus on Transaction Commit」のような固有名）
- コードの識別子や設定値（`Suspended`、`0.5 BTC` のような、日本語にすると別物になる断片）
- 日本語で説明した後に「（原文では「...」）」と原文を添える形。この形は訳が本文側にあるので、括弧を二重にしない

### 訳文は、英語の構造をそのまま日本語へ移さない

関係節を連体修飾へ直訳すると、修飾が長くなり、読点で無理に繋ぐ形になる。読点の後ろに名詞が来て、そこまでの述語が全部その名詞に掛かる文は、この失敗である。

| | 例 |
|---|---|
| 原文 | `SQLite uses a cost-based query planner that estimates the CPU and disk I/O costs of various competing query plans` |
| 修正前 | SQLite は、競合する複数の実行計画について CPU とディスク入出力のコストを見積もる、コストに基づいたクエリプランナを使う |
| 修正後 | SQLite はコストに基づいたクエリプランナを使い、競合する複数の実行計画について CPU とディスク入出力のコストを見積もる |

修飾される名詞（クエリプランナ）を先に出し、関係節の内容は述語で受け直す。同じ直し方が要る形をもう 2 つ挙げる。

| 修正前 | 修正後 |
|---|---|
| 問い合わせの木へ適用する規則を、システムカタログに格納された中から探す | システムカタログに格納された規則の中から、問い合わせの木へ適用できるものを探す |
| 〜を理解するために必要な意味の解釈を行う | 〜を参照しているのかを解釈する |

2 つ目は、英語の名詞句（semantic interpretation）を名詞のまま訳して §11「名詞へ言い換えない」に触れた例である。訳文にも本文と同じ文体ルールが掛かる。

### 訳を足したら、地の文の重複を削る

引用の直後に「〜という内容です」「〜と書いています」と同じ事を日本語で言い直している段落は、訳を足すと 2 度同じ説明が並ぶ。訳を入れた時点で、その言い直しは消す。残すのは、原典が言っていない事（そこから何が読み取れるか、読者が何をすればよいか）だけである。

- 修正前: 「Policy is not applied to transactions in blocks」（policy はブロックに入った取引へは適用されない）という一文があります。ブロックに入った取引へ policy は適用されず、判定に使われるのは consensus rule だけという事になります。
- 修正後: 「Policy is not applied to transactions in blocks」（policy はブロックに入った取引へは適用されない）という一文があります。判定に使われるのは consensus rule だけ、という事になります。

### 引用元のページは、原典を開いて選ぶ

引用が主題の中心に近いほど、どのページから引くかで説明の正確さが変わる。記憶で書かず、`WebFetch` で原典を取得し、逐語である事と、その文が説明したい段階の記述である事を確かめる。2026-08-11 の query-processing では、parse tree と query tree の区別を書くために、引用元を PostgreSQL の query-path.html から parser-stage.html へ差し替えた。前者は 4 段階の概観で、段階の中の分かれ目は後者にしか書かれていない。

## 24. 用語は、ノートをまたいで 1 つに決める

同じセクションのノートは続けて読まれるので、同じ物が別の名前で出てくると、読者は別の物かどうかを考える事になる。新しいノートで用語を選ぶ前に、同セクションの既存ノートを `grep` して、既に通っている表記へ揃える。

- 2026-08-11 の database-systems では、index の訳を「索引」で統一している（b-tree で 45 回、soft-delete で 6 回、query-processing で 15 回）。ここに 1 本だけ「インデックス」で書いたノートを足さない
- 併記するのは初出の 1 回だけにする（「索引（インデックス）」）。2 回目以降は選んだ側だけで通す
- どちらを選ぶか迷ったら、既存の使用回数が多い方に倒す。既存が 0 本なら、原典と `CREATE INDEX` のような読者が打つ語からの距離で決める

判定は書き終わってからでは遅い。表記を変えるとノート全体の置換になるので、Step 3（既存ノートの把握）で決めておく。

### 自分が持ち込んだ語は、過去記事の実測で検める

既存ノートに前例が無い語は、書き手の語彙ではなく執筆側が持ち込んだ語である可能性がある。ノートだけを見ていると、自分で増やした用例が根拠に見えてしまう。判定は `content/post/ja` の実測で行う。

2026-08-12 に「Database Systems で製品と出てくるが、プロダクトのほうが自然ではないか」と指摘を受けて数えた結果が次である。

| 語 | 技術記事 221 本 | notes |
|---|---|---|
| 実装 | 584 | 138 |
| DBMS | 21 | 1 |
| 製品 | 14 | 34 |
| プロダクト | 12 | 2 |

過去記事では「製品」14 対「プロダクト」12 で拮抗していて、どちらも定着していない。一方 notes では「製品」が 34 回に膨れていた。執筆側が持ち込んだ語である。

置き換え先は、指摘された「プロダクト」でもなかった。実測で同じく少数派であり、§3 の「日本語で書けるものは日本語で」にも逆行する。正しかったのは、その分野で対象を正確に指す語（DBMS）と、書き手が既に使っている語（実装）である。ユーザーの依頼文に出てくる語彙も手がかりになる（このときは「DBMS によって挙動が異なり得る点」と書かれていた）。

手順は 3 つである。第一に、ノートで 10 回以上使った語のうち、既存ノートに前例が無い物を挙げる。第二に `grep -ro "<語>" content/post/ja/ | wc -l` で数える。第三に、少数派なら、その分野の標準語彙か書き手の多数派の語へ置き換える。置換した後は、日本語との間の空白（`DB が` に揃えて `DBMS で`）と、読点の直後に空白を入れていないかを確かめる。

使用回数が 1〜2 回でも、見出しに出た語は同じ手順で検める。本文が別の語で通っているのに見出しだけ持ち込んだ語になる、という割れ方をする。2026-08-13 の Foreign Key では、本文が「担当」で 3 回通っているのに、見出しだけが「担い手」だった（既存ノートにも過去記事にも用例 0 件）。見出しは目次で単独に並ぶので、本文との食い違いが読者に見えやすい。

同じ問いに答える見出しが姉妹ノートにあるなら、形もそろえる。「〜を張らない場合、誰が◯◯を守るのか」のような問いの形で 2 本を並べると、読者は同じ構造の話だと分かる。片方だけ体言止めや名詞句にしない。

### 後半で否定する物を、前半で無条件に例示しない

記事の後半で問題として扱う書き方を、前半で解決策として素朴に出すと、読者はそれを推奨だと受け取ったまま後半に入る。前半で出す時点で、後半との違いを 1 文で断る。

- 修正前: 「`COALESCE(age, -1) <> 20` のように `NULL` を別の値へ置き換えてから比べます」（後半で sentinel value を問題として扱う）
- 修正後: 「〜比べる方法もあります。ここでの `-1` は問い合わせを評価する間だけ使う値で、表へ `-1` を保存する設計とは別です」

書き上げたら、後半で否定した物の名前（sentinel value・削除フラグ・共有 DB）で全文を `grep` し、前半に断りなしの用例が無いかを見る。

### 主題でない「〜とは何か」論争へ踏み込まない

定義を強く書くと、主題と関係のない議論を呼ぶ。`NULL` を「値ではない」と書くと、読者は「値か否か」を考え始める。記事の目的がその論争の決着でないなら、性質だけを書いて先へ進む。

- 修正前: 「SQL の型が持つ値の 1 つではなく、値が入っていないという状態そのものを指します」
- 修正後: 「値が存在しない事や不明である事を表すために SQL が特別扱いする印です」

判定は「その定義に反論する読者が居た時、記事の主張が変わるか」で行う。変わらないなら、その定義は書かなくてよい。

## 25. 出典を、本文の主語にしない

一次資料を確かめて書くほど、文が資料に寄る。「◯◯氏は〜と述べています」で段落を始め、英語を引き、訳を付け、そこから説明へ戻る形が節ごとに並ぶと、ノートは調査メモの読み味になる。読者が知りたいのは資料の内容ではなく、その概念をどう理解すればよいかである。

正確さと引き換えにする話ではない。原典と記事側の整理を書き分ける規則（`precision_claims.md` §40）はそのまま掛かる。減らすのは、資料を文の主語に置く回数と、裏付けだけが目的の引用である。

### 説明を先に組み立て、後から根拠を戻す

出典リンクを 1 つも置かずに本文を書き、書き上がってから根拠が要る所へリンクと引用を入れる。この順で作ると、リンクを全部隠しても本文が成立する。逆順で作ると、リンクを外した時に崩れる文章ができる。

### 引用を残す条件

英語の原文と訳を置くのは、原文の表現そのものに意味がある時だけにする。

- 原則そのものを紹介する（原著者の言い回しが定着している）
- 用語の定義を厳密に示す
- 原著者の強い表現を、弱めずに渡す事に意味がある

事実の裏付けだけが目的なら、日本語で書いて出典名へリンクを張る（→ §14 型4）。1 本のノートで英語の引用が 3 個を超えたら、どれが上の 3 条件に当たるかを数え直す。

### 概念を主語にする

| 修正前 | 修正後 |
|---|---|
| Hodgson 氏は、削除タスクをバックログへ積む運用を紹介しています | Release Toggle は全体公開が終われば役目も終わるので、追加した時点で削除タスクまで作っておく運用が効きます |
| Hodgson 氏は 2 つの軸を分類に選んでいます。「two major dimensions: ...」（〜という 2 つの主要な軸） | Feature Flag は、どれくらい長く残るかと、判断がどれくらい動的かの 2 軸で整理できます |

人名を主語にしてよいのは、その人の判断や評価そのものが主張の一部になっている時（原典が 2 つの方式のうち一方を勧めている、など）に限る。同じ人名が 3 回以上、文の主語に立っていたら数え直す。

なお、人名を出す時に敬称「氏」を付ける規則（§12）はそのまま掛かる。回数を減らす事と、出した時の書き方は別の話である。

### 識別子を主語にしない

人名と同じ問題が、版番号・草案番号・規格番号でも起きる。「draft-07 は 409 を返す事を推奨しています」「draft-07 は 422 を割り当てています」「draft-07 は、検出の方法までは定めていません」と続くと、読者は 3 回とも「draft-07 とは何だったか」を思い出す作業をする。人名と違って識別子は意味を持たない記号なので、思い出せなければ文が読めない。2026-08-19 の idempotency で「どの話か覚えてられない単語を主語に選ばないでほしい」という指摘を受けた。

対象は、それ自体では中身を思い出せない識別子である。

- 版番号・草案番号・規格番号（draft-07、v2.1、RFC 9110、ISO/IEC 9899）
- 記号だけの識別子（CVE-2021-44228、ADR-005、節番号）
- 記事が自分で付けた略号（「方式 A」「作り 1」）

初出で何をする物かを書いて紹介し、以降は概念か、その仕様が定めている物を主語にする。

| 修正前 | 修正後 |
|---|---|
| draft-07 は、同じキーの要求がまだ処理中の場合に 409 を返す事を推奨しています | 処理中の要求と同じキーが届いた場合の応答には、409 が推奨されています |
| draft-07 は、検出の方法までは定めていません | 処理中をどう検出するかは、仕様の範囲外です |
| RFC 9110 は、非冪等なメソッドの自動再試行を SHOULD NOT としています | 非冪等なメソッドの自動再試行は、原則として避けるよう定められています |

同じ識別子が 3 回以上、文の主語に立っていたら数え直す。判定は「その識別子を隠して読んだ時、文が何の話か分かるか」で行う。

`precision_claims.md` §40（原典が述べた事と記事側の整理を書き分ける）と衝突させない。減らすのは主語の位置に置く回数であって、帰属そのものではない。「〜と定められています」「仕様の範囲外です」は、受動で帰属を保ったまま主語を概念へ渡す形である。帰属先が本文のどこにも無い状態にはしない。

識別子そのものが主張の一部になっている時（版によって挙動が違う、失効している事が論点である、など）は主語にしてよい。

### 「〜を以下に示します」で図と表を導入しない

定型で図を導入すると、本文が前置きだけで進む。本文の説明が図の内容へ着地する形にすると、前置きの 1 文が要らなくなる。

- 修正前: 「4 分類を以下に示します。」
- 修正後: 「この 2 軸から、Release・Experiment・Ops・Permissioning の 4 種類に整理できます。」（この直後に表を置く）

図の後で、図に描いてある事を文章で言い直さない。残すのは、図から読み取れない含意だけである。

### 原典の構成をなぞらない

原典が A → B → C → D で説明していても、読者にとって A → C → B が速いならそちらを選ぶ。並べ替えてよいのは順序だけで、原典が示した因果と主張は変えない。

### 段落は 1 つの論点で閉じる

依存の注入・factory・fallback・隠蔽・Context の設計のような関係する話題を 1 段落へ混ぜると、読者は関係を自分で組み立てる事になる。関係が分かる順序へ割る。

- 何を隠したか → その結果どこを変えやすくなったか → 依存をどこで組み立てるか → 評価に失敗した時にどこへ落ちるか

抽象的な説明が 2 文続いたら、その場で具体例を 1 つ置く。「判断の動的さには複数の種類があります」で止めず、「Release Toggle は起動時に決まれば足ります。Experiment Toggle はユーザごとに結果が変わるので、リクエストごとに評価します」まで書く。

## 26. 文章を実況しない

2026-08-18 に本人から受けた指摘。節の冒頭に「これから何を説明するか」を説明する文が入りやすい。この種の文は内容を増やさず、書き手が自分の文章構成を実況しているように読める。

- 「本ノートで、説明する範囲も決めておきます。」
- 「まず、前提を整理しておきます。」
- 「ここで用語を整理しておきます。」
- 「次に、具体的な実装を見ていきます。」
- 「以下では、この違いについて説明します。」
- 「ここからは、〜について考えます。」

原則として削り、説明したい内容そのものから書き始める。

### 書き換えの型

| 修正前 | 修正後 |
|---|---|
| 本ノートで、説明する範囲も決めておきます。ここでは On と Off の 2 値を返す Boolean Flag を中心に扱います。 | 本ノートでは、On と Off の 2 値を返す Boolean Flag を中心に扱います。 |
| まず、Feature Flag が必要になる理由を整理します。Feature Flag はデプロイとリリースを切り離します。 | Feature Flag はデプロイとリリースを切り離します。 |
| 次に、Toggle Router の実装を見ていきます。 | Toggle Router へ判断を集約すると、業務ロジックは flag の名前や取得方法を知らずに済みます。 |

### 避ける表現

- 「〜を見ていきます」「〜を考えてみます」「〜を整理します」「〜を確認します」「〜について説明します」
- 「〜も決めておきます」「〜を押さえておきます」
- 「ここでは〜を扱います」だけの単独段落
- 「まず」「次に」「最後に」を、文章の構成の説明として使う形（処理の順序を説明する「まず prepare を送ります」は対象外）
- 「以下に示します」だけで図や表へ接続する形（→ §25）
- 「本ノートでは」を節ごとに繰り返す

### 例外

短い導入文を置いてよいのは次の場合である。ただし、その場合も「これから説明します」「整理しておきます」の実況にせず、内容を直接述べる。

- ノートの対象範囲を明示しないと誤読される
- 意図的に扱わない範囲を明示する必要がある
- 前の節から論点が大きく変わり、接続が無いと読みにくい
- 読者が前提条件を知らないと、後続の説明を誤解する

「本ノートでは」は、実際に情報を持つ文であれば使ってよい。「本ノートでは Boolean Flag の分岐設計と削除運用を扱い、boolean 以外の値を返す flag や製品選定は対象外とします」は範囲そのものを伝えているので残す。

### 判定

各段落の 1 文目について、その文を消しても後続の意味がそのまま通るかを見る。通るなら、その文は実況である可能性が高い。

「これから何を話すか」「今どの段階にいるか」「文章をどう構成したか」しか伝えていない文は削る。技術ノートは、筆者が読者へ技術を説明する文章であって、生成手順の実況ではない。

## 27. 出典を「原典」と呼ばない

2026-08-18 に本人から受けた指摘。本文で出典を指す時に「原典」と呼ばない。設計パターンや考え方を説明するノートには大げさで、学術的・権威的に読める。Web 記事・ブログ・論文・書籍と種類の違う出典を、1 つの語でまとめてしまう点も正確ではない。

### 書かない形

- 「原典では」
- 「原典によると」
- 「原典が問題にするのは」
- 「原典も〜を勧めている」
- 「原典の例では」
- 「原典に従うと」

### 代わりに書く形

情報源の種類と文脈に合わせて具体的に書く。

| 出典の種類 | 書き方 |
|---|---|
| ブログ・Web 記事 | 「King 氏の記事」「前述の記事」「この考え方を示した記事」 |
| 論文 | 「論文」「◯◯氏らの論文」 |
| 書籍 | 「書籍」または書名 |
| 仕様 | 仕様名 |
| RFC | RFC 番号、または「RFC」 |
| 公式ドキュメント | 「PostgreSQL のドキュメント」のように製品名・プロジェクト名を付ける |

誰の主張かが説明に効くなら、著者名を主語にする（回数の上限は §25）。出典を明示しなくても文が成り立つなら、出典への言及ごと削る。

「元記事」への一律置換は避ける。引用対象が論文や書籍の時に「元記事」と書くと不正確になるため、必ず情報源の種類へ合わせる。

### 書き換えの例

| 修正前 | 修正後 |
|---|---|
| 原典では、複数段階の parse も認められています。 | King 氏は「Don't be afraid to parse data in multiple passes.」と書いています。 |
| 原典が問題にするのは、検査の重複です。 | 問題になるのは、検査コードが処理の途中へ散らばる事です。 |
| 原典も、内部表現を隠す形を勧めています。 | King 氏は、内部表現を隠す形を勧めています。 |

### 権威付けの言い回しと同じ扱いにする

「原典では〜」は、「本質的には〜」「重要なのは〜」「注目すべきなのは〜」と同じ型の権威付けである（→ §3、§11）。書きたい事があるなら、具体的な事実・著者・仕様をそのまま主語にする。

既存のノートを直す時も、「原典」が残っていれば削除の対象として扱う。`scripts/style_check.sh` が本文中の「原典」を [NG] として検出する。

## 28. 自分が言わない言い回しを増やさない

規則を足す度に、その規則を避けるための言い回しが生まれる。「〜と言えます」を禁じれば短い自動詞（要る・決まる・残る）へ、「このノートでは」を禁じれば「ここでは」へ逃げる。逃げ先が定型になると、規則は全部守っているのに本人の文体から離れる。

実測と置換表は `voice_markers.md` にある。書き終えたら `scripts/style_check.sh` の `[NG] 本人が使わない言い回し` と `[INFO] 文体距離` を潰す。閾値は本人の記事で誤検出が 0 になるよう合わせてあるので、出たら本文の側を直す。

新しい規則をこのガイドへ足す時は、置き換え先の言い回しを 1 つ決めて書く。決めずに禁止だけ足すと、次のノートで別の逃げ先が育つ。
