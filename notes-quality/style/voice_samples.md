# 文体の手本（本人の地の文）

ノートの文体は、規則ではなくここに写した実文で掴む。全て `content/post/ja` からの引用で、加工していない。ブログ記事の一人称・体験の記録はノートへ持ち込まないが（→ `writing_style.md` §1）、**文の作り・接続詞・文末・図と表への繋ぎ方**はそのまま使う。

規則だけを読んで書くと、規則を守った別の文体ができる。ノート 47 本で実際にそれが起きた（→ `voice_markers.md`）。書く前にここを読み、書いた後に自分の草稿と並べる。

**SKILL.md とガイド類の地の文は手本にしない。** ガイドは である体の指示文で、圧縮された言い回し（要る・へ・そのもの）で書かれている。写すのはここだけである。

## 1. 仕組みを説明する（技術ノートに一番近い）

> Parquet の読み込みでは、ファイルが持つ型情報を捨てて全カラムを TEXT として SQLite に格納していました。そのため `MAX(price)` や `ORDER BY price` が文字列として評価され、同じデータでも CSV と Parquet で SQL の結果が変わる状態でした。エラーも警告も出ません。

> ファイル出力では、一時ファイルから出力先へコピーする途中でディスクフルや I/O エラーが発生すると、既存ファイルが途中まで上書きされた状態で残るケースがありました。現在は、一時ファイルへの書き込みが完了してから出力先へ反映し、失敗時に既存ファイルを壊さないようにしています。

（`2026-08-09-【golang】…sqlyをv1.0.0にする話`）

取る所: 「〜では、〜します」で主語と場面を先に置く。「そのため」で因果を繋ぐ。最後に短い一文（「エラーも警告も出ません。」）で効き目を言い切る。名詞化（「上書きの発生」）に逃げず、動詞で書いている。

## 2. 2 つの物を比べる

> sqly と DuckDB は、主目的が違います。DuckDB は分析 DB そのものであり、ファイル読み込みは DB へデータを入れる手段です。sqly は「手元のファイルをサッと SQL で閲覧・編集すること」が主目的で、DB はファイルを触るための手段です。この違いが機能差を生んでいます。

（同上）

取る所: 何が違うかを 1 文目で宣言してから、両方を同じ形の文で並べる。対比の軸を先に出すので、読者は表を読む前に軸を持てる。

## 3. 定義を置く

> markdown ライブラリは、Builder Pattern（メソッドチェーン）で Markdown を組み立てるライブラリです。html/template のようなテンプレートエンジンは使いません。生成する記法は、GitHub Markdown に従います。
>
> 対応範囲は、見出し、リスト、チェックボックス、テーブル、コードブロック、引用、水平線、文字装飾、リンク、画像、details、脚注、数式、アラートです。

（`2026-08-13-【golang】markdownとmermaidを生成する…`）

取る所: 定義は「A は、〜する B です」で 1 文。直後に「〜は使いません」と、隣にある別物を短く外す。括弧は言い換えの置き場所として使う。

## 4. 図と表へ繋ぐ

> 上記の図を見て分かる通り、加盟店とカード会員だけでは決済が閉じません。加盟店の裏には Acquirer が存在し、その先に Brand、Issuer がいます。Issuer は決済を受け付けるかどうかを返し、Brand〜加盟店まで伝わります。例えば、利用上限に引っかかった場合は、Issuer は 決済を拒否します。

> ISO 8583 は、カード起点の金融取引メッセージを表現する国際標準であり、オーソリゼーションなどで利用されます。以下のような特徴があります。

（`2026-06-07-クレカ決済で用いる通信規格ISO 8583の概要と…`）

取る所: 図を指す語は「上記の図」（「上図」は本人が 62 万字で 1 回しか書いていない）。図の後は、図に描いていない含意（誰と誰では閉じないか）を足す。表と箇条書きの導入は「以下のような特徴があります」「以下が実行例です」「以下、〜の特徴（抜粋）です」で受ける。

## 5. 判断と留保を書く

> 大前提として、runn は API サーバー寄りのテスト、ShellSpec はシェルスクリプト寄りのテストに最適化されたテスティングフレームワークと言えるでしょう。どちらも素晴らしいツールであり、CLI のテストにも利用できます。
>
> しかし、これらのツールでは私のユースケースに合わない部分がありました。

（`2026-07-04-CLIにブラックボックステストE2Eを行うatagoを作った話`）

取る所: 対象の良い所を先に認めてから「しかし、」で自分の立場を出す（→ `writing_style.md` §15）。逆接の主力は「ただし」ではなく「しかし」である。

## 6. 道具の働きを書く

> omokage は、過去の文章から「あなたの書き方」を学習し、新しい下書きがその文体にどれだけ近いかをスコアで返してくれる CLI ツールです。
>
> 全ての処理がローカルで完結し、日本語と英語の両方で動作します。学習した文体は SQLite のデータベースとしてローカルに保存されるだけで、ネットワークには一切アクセスしません。

（`2026-06-02-文体の一致度を評価するomokageを作った話`）

取る所: 「〜してくれます」で道具の働きを書く。制約は「〜だけで、〜しません」と、範囲と否定を 1 文へ収める。

## 7. 前提を外して読者を戻す

> より厳密には、決済の取消や返金などがありますが、本記事内では BASE I/Ⅱ の存在が理解できていれば問題ありません。

（`2026-06-07-クレカ決済で用いる通信規格ISO 8583の概要と…`）

取る所: 扱わない範囲は、読者が「足りないのでは」と思う場所で短く外す。ノートでも「本記事では」のまま使う（2026-11-02 更新。→ `writing_style.md` §0）。

## 8. 著者が調整したノート（Wallet）

ここから下は `content/notes/blockchain-systems/wallet/index.md` からの引用である。AI の草稿を著者が「納得できるレベル感まで調整した」ノートで（2026-11-02 ユーザー談）、ノートの構成と文の運びはここが一番近い。ただし表記は調整の対象外だったので、「ユーザ」「事」はそのまま写さず、`writing_style.md` §0 の「ユーザー」「こと」に直す。

> ウォレット（wallet）は、Bitcoin などの暗号資産を受け取り、残高を確認し、他の相手に送るためのソフトウェアです。PC やスマートフォンの画面で操作するタイプと、コマンドを入力して操作するタイプがあります。

> 本記事では、ウォレットを初めて学ぶ人に向けて、OSS（Open Source Software）の実例から、機能の違いとその理由を説明します。基本機能と操作画面を確認した後、次の疑問を順に扱います。

取る所: 1 文目で何をするソフトウェアかを言い、2 文目で種類を示す。参考画面を挟んでから「本記事では」で読者と範囲を宣言し、扱う疑問を箇条書きで並べる。

> 誰でも参加できるネットワークでは、「このアドレスから送ります」という申告だけで送金を認めると、他人の資産も使えてしまいます。一方、ノードに秘密情報を渡して本人確認をすると、受け取ったノードも同じ操作ができるようになります。必要なのは、次の条件を満たす承認方法です。

取る所: 仕組みの名前より先に、素朴なやり方が壊れる様子を 2 つ書き、要件を箇条書きにしてから「このために使うのが、秘密鍵とデジタル署名です。」で仕組みを出す。

> 署名は内容を隠す暗号化ではありません。Bitcoin や Ethereum では、送金先や金額などを他の参加者も確認できます。また、署名が正しくても、送金先が信頼できるとは限りません。

取る所: 定義の直後に、読者が混同しやすい隣の概念を短い否定文で外す。外した理由を次の 1 文で具体的に書く。

> 上記に加えて、何を細かく操作したいか、誰と資産を管理するかによって、必要な機能が変わります。例えば、次の OSS にはそれぞれ特徴があります。取り上げた機能は、その製品だけにあるとは限りません。

> 送金処理をユーザ・ウォレット・ネットワークに分けると以下のようになります。

> 対象とした 5 種類を整理すると、以下の通りです。

取る所: 表・図の直前は「例えば、次の〜」「〜に分けると以下のようになります」「整理すると、以下の通りです」で受ける。例を出したら、その例が全体ではないことを 1 文で断る。

> 画面を開く場所と、秘密情報を保管する場所は、同じとは限りません。画面に表示する残高は、チェーン上の記録から確認します。この関係を理解するために、暗号資産が使われる理由と、取引の記録方法から見ていきます。

取る所: 節の終わりで、ここまでで分かった区別を 1 文で言い、次の節を読む理由に繋ぐ。

> 問題は、「取引を中継するサーバが返した文章」が「ウォレットの開発元による更新指示」のように読めた事です。開発者は 3.3.3 より前の表示を問題として説明し、更新は公式サイトから行うよう案内しています。

取る所: 事故は、起きたことを先に書き、何と何の区別が崩れたかを「問題は、〜です。」で 1 文に絞る。調査者・開発者の見解は主語を立てて分ける。

## 数字で見た本人の地の文

自分の草稿がここから離れていないかを見る目安である（本人の技術記事の実測）。

| 指標 | 本人 | 外れている時の症状 |
|---|---|---|
| 一文の長さ（中央値） | 46 字 | 30 字前後の断定が並ぶと、箇条書きを地の文に流した読み味になる |
| 一文あたりの読点 | 1.45 個 | 1.0 を切ると、切り詰めた短文の連続になっている |
| 「しかし」「例えば」「そのため」「ちなみに」「つまり」の合計 | 千字あたり 1.4 個 | 0.5 を切ると、接続詞を削りすぎている |
| 助詞「へ」の比率（に + へ の中） | 3% | 10% を超えたら「へ」を「に」へ戻す |

ノートは定義と構造を書く分だけ本人のブログより硬くなるが、上の 4 つが本人の半分を割ったら、規則に寄せすぎて別の文体になっている。
