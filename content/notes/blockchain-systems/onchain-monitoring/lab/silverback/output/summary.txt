Silverback 0.7.39 の欠けの実験（2026-11-23、SCENARIOS.md に従う）

版: silverback 0.7.39 / eth-ape 0.8.54 / ape-foundry 0.8.13 / web3 7.16.0 / taskiq 0.12.6 / anvil 1.7.1 / solc 0.8.28 / Python 3.12.12（venv/）
置き場所: drive.py（driver）、botproj/（bot.py・ape-config.yaml・token_abi.json）、sbproxy.py（HTTP+WS の故障中継）、sink_ctl.py、common.py、make_summary.py
実行: venv/bin/python drive.py S0 S1 S2 S3 S4 S5 S1-a-poll S1-b-poll S3-poll
ポート: anvil 18736、sbproxy 18737（control は /control）、sink 18738。すべて 127.0.0.1。

共通の道具からの差分（理由つき）
- faultproxy.py は HTTP だけなので、既定の WebsocketRunner（eth_subscribe）を挟めない。ape-foundry は ws URI を
  http の host から作る（provider.py の ws_uri = "ws" + uri[4:]）ため、同じポートで HTTP と WS を受ける sbproxy.py を書いた。
  故障の規則と JSONL の形は faultproxy.py と同じ。WS では fail_blocks のブロックの通知（newHeads/logs）を捨て、down では WS を 1011 で閉じて新しい接続を 503 で断る。
- sink.py は「最初の N 件」なので、時間で 500 に切り替える sink_ctl.py（POST /__control）にした。
- bot が起動を終える（約 3.4 秒）まで空のブロックを作り、起動後の最初のブロックから送金を入れた。量 = ブロック番号は同じなので、量は 2 からでなく 6 前後から始まる。
- S1 の失敗ブロックは「起動後 14 件目」（=19）。S2 は 9 件目が届いた所で止めた。
- bot は文書の例どおり on_startup で遡らない。ハンドラは requests.post の後 raise_for_status（S4-noraise だけ呼ばない）。
- S2 の 2 回目以降に出る「exited by itself」は、driver が自分で止めたのを数えた誤記（後で直した）。自発の終了ではない。

======== 読み取り（実測と、理由を確かめたソースの場所）========
S0  Websocket・Polling とも 40/40、二重なし。受信は送金の約 0.01〜1 秒後。
S1  Websocket: ブロック 19 の通知（logs と newHeads）を中継で捨てると、量 19 は永久に届かない。(a)(b) とも同じ（押し付けの通知は再送されない）。
    ログには何も出ない。bot は生きたまま 20 以降を通常どおり通知する。runner.py の WebsocketRunner._event_task は届いたログを run_task するだけで、ブロック番号の飛びを確かめない。
    Polling: eth_getBlockByNumber(19) が 1 回 error になった時点で "ERROR: Block with ID '19' not found" を出して bot が終了（exit 0、t=19.6 s）。
    量 19 以降は (a)(b) とも届かない（20 秒後に回復しても bot は戻らない）。
S2  SIGTERM: 停止中の 60 件＋再起動の約 3.5 秒の分＝64 件（量 15〜78）が消えた。state.json には last_block_seen=14 が残るが、
    runner.startup は それを on_startup に渡すだけで、自分では遡らない（runner.py startup）。再起動後は head から。
    SIGKILL: state.json 自体が書かれていない（_checkpoint は終了時と 1 分ごとの cron ループでしか呼ばれない。今回は起動 12 秒で kill）。63 件消えた。
S3  Websocket: 置き換わった 21〜23 の通知は残ったまま、新しい 1021〜1023 も届いた（6 件とも removed=false）。取り消しなし。
    中継の記録では Anvil 1.7.1 の logs 購読は anvil_reorg で removed:true のログを 1 つも流していない。ノードが流さないので、log.removed で取り消す書き方はこの環境では試せていない。
    Polling: ape が "ERROR: Chain has reorganized since returning the last block" を出すが、取り直すのは新しい head（24）だけ。
    1024 は届き、1022・1023 は届かない。22〜24 の旧通知は残ったまま。ape_ethereum/provider.py の poll_blocks は reorg 時 next_block = adjusted_head.number にするため、分岐点まで戻らない。
S4  raise_for_status あり: 500 が 4 回続いた所で bot が終了（max_exceptions=3 を超えた。runner.py run_task の sum(self.exceptions.values()) > max_exceptions で Halt）。
    終了コードは 0（_cli.py は asyncio.run(runner.run()) を呼ぶだけで、Halt は run() の中で握られる）。再起動の仕組みが「異常終了だけ再起動」なら戻らない。以後の 80 件が消えた。
    raise_for_status なし: bot は生きたまま、500 の 60 件はそのまま捨てられ、ログにも何も出ない。回復後の 20 件は届いた。
S5  Websocket を閉じた直後に ConnectionClosedError で bot が終了（exit 1）。5 分後に RPC が戻っても bot は戻らないので、以後の 330 件はすべて消えた。
    再接続の試みはない（runner.py の WebsocketRunner.run は AsyncWeb3(WebSocketProvider) を 1 回開くだけ）。
    手元の health/metrics の口は無いので、外から分かるのはプロセスの有無だけ（10 秒ごとの標本は t=13.4 s 以降ずっと alive=false）。
    注意: 中継は 1011 で能動的に閉じた。TCP が黙って切れる形の障害は試していない。
