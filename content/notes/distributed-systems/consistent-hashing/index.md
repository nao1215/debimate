Consistent Hashing（コンシステントハッシュ法）は、キーとサーバーを同じ円の上に置き、キーを円の上で次にあるサーバーへ渡す振り分け方です。この円をリングと呼びます。Karger 氏らが [1997 年の論文](https://doi.org/10.1145/258533.258660)で、Web のキャッシュに要求が集中するのを和らげる目的で提案しました。

英語版 Wikipedia の [Consistent hashing](https://en.wikipedia.org/wiki/Consistent_hashing) の項によると、この方法はキャッシュのキーをサーバーへ均等に配り、n 台目のサーバーを足しても移るキーは全体の 1/n だけです。キャッシュのサーバーを 3 台から 4 台に増やす実験で、この 2 つが成り立つかを調べました。以下は、10 万個のキーを 3 通りの方法で振り分けた結果です。

{{< figure src="images/consistent-hashing_cover.webp" alt="3 通りの振り分け方ごとに、3 台の時と 4 台に増やした後の、各サーバーが持つキーの割合を横棒で並べた図。台数で割る方法は 33% ずつから 25% ずつになるが、動いたキーは 75.0%。リングに 1 台 1 点を置く方法は 3 台の時点で 48%・17%・35% と偏り、4 台目の cache-4 が cache-1 から 39% を取って一番多くなり、動いたキーは 38.9%。1 台に 100 点を置く方法は 34%・34%・32% から 24%・24%・25%・27% になり、動いたキーは 26.7%" caption="キー 10 万個を 3 台から 4 台に増やした時の、各サーバーが持つ割合と動いたキー" align="center" >}}

台数で割る方法では 75% のキーが別のサーバーに動きました。リングでも 1 台が 1 点だけだと、3 台の時点で cache-1 が 48% を持ち、足した cache-4 は cache-1 だけから 39% を取りました。cache-3 は 35% のまま減りません。名前に番号を付けて同じサーバーを 100 か所に置くと、動いたのは 26.7% で 1/4 に近く、3 台から少しずつ移りました。2 段目と 3 段目の違いは、1 台を円の何か所に置くかだけです。

Consistent Hashing を使うのは、キーで振り分ける先が複数台あり、その台数が変わる時です。キャッシュサーバーである memcached のクライアント、Web サーバーの nginx が持つ `hash ... consistent`、分散 DB（データベース）である Cassandra のトークン、プロキシである Envoy のロードバランサーなどに入っています。台数を増やした直後にキャッシュの外れが増えて DB の負荷が上がった、増やしたのに 1 台だけ忙しいまま、という形で出会います。

<br>

本記事では、これから Consistent Hashing を使う人と、既存のシステムで設定に出会った人に向けて、次の疑問に答えます。

- 台数で割る方法では、なぜ 1 台足すだけで大半のキーが動くのか。
- リングでは、なぜ動くキーが減るのか。
- 1 台に 1 点のリングは、なぜ偏るのか。点はいくつ置けば良いのか。
- 複製をリングで次に来る点に置くと、何が起きるのか。
- 人気のキーに集まる要求は、点を増やせば分かれるのか。
- Jump Consistent Hash・Rendezvous・Maglev とは何が違うのか。

### 台数で割ると 3/4 が動く

キーを整数に変える関数を[ハッシュ関数](/notes/blockchain-systems/hash-function/)と呼び、その出力をハッシュ値と呼びます。同じキーからは、どこで計算しても同じ値が出ます。

最初に思い付くのは、キーのハッシュ値をサーバーの台数で割り、余りを番号とするサーバーへ送る方法です。本記事の実験は Python の標準ライブラリだけで書き、キーとサーバー名の位置は、[hashlib](https://docs.python.org/3/library/hashlib.html) で求めた MD5 の先頭 8 バイトで決めました。数えるのはキーの保存先が変わった数で、データの転送量や時間ではありません。コードと出力の全体は [lab/](https://github.com/nao1215/debimate/tree/main/content/notes/distributed-systems/consistent-hashing/lab) にあります。台数で割る方法は次のように書きました。

```python
from hashlib import md5

def h(text):
    return int.from_bytes(md5(text.encode()).digest()[:8], "big")

def mod_n(servers):
    n = len(servers)
    return [servers[h(k) % n] for k in KEYS]  # KEYS は "user:0" から "user:99999"
```

3 台なら `h % 3`、4 台なら `h % 4` で保存先が決まります。3 で割った余りと 4 で割った余りの組み合わせは、ハッシュ値が 12 増えるごとに同じ並びを繰り返します。12 は 3 と 4 の最小公倍数だからです。この 12 通りの中で 2 つの余りが一致するのは、12 で割った余りが 0・1・2 の時だけなので、残るキーは 3/12 = 1/4 で、残りの 3/4 が動きます。

冒頭の図にある 75.0% は、この計算の通りです。N 台から N+1 台にすると動く割合は N/(N+1) で、台数が多いほど 1 に近づきます。顧客をセルへ振り分ける [Cell-based Architecture](/notes/software-architecture/cell-based-architecture/) でも、剰余で分けると同じことが起きます。

キャッシュなら、動いたキーは新しい保存先で外れ、DB に読みに行きます。そのため、台数を増やして負荷を下げるつもりが、増やした直後に 3/4 のキーが DB へ向かうことになります。データを保存するサーバーなら、動いたキーの分だけデータのコピーが必要です。[OpenStack Swift](https://docs.openstack.org/swift/latest/ring_background.html) がリングを採用した経緯も、この剰余の問題から説明されています。

### リングに置くと、足した 1 台の分だけが動く

Consistent Hashing では、ハッシュ値の範囲（実験では 0 から 2^64 − 1）の両端をつないで円にします。リングはハッシュ値の並べ方を表したもので、サーバーを円形につなぐわけではありません。

サーバーは名前から求めたハッシュ値の位置に置き、キーも自分のハッシュ値が指す位置から時計回りに進んで、最初に出会ったサーバーに行きます。冒頭の図で 2 段目のリングについて、点を実際の位置に置いて描き直したのが次の図です。

{{< figure src="images/consistent-hashing_ring.webp" alt="左は 3 台のリングで、cache-1・cache-3・cache-2 の点の手前の弧がそれぞれのキーになり、48%・35%・17%。右は cache-4 を足した後で、cache-4 の点が cache-2 と cache-1 の間に入り、全体の 39% にあたる弧を cache-4 が取って cache-1 は 10% になる。cache-2 と cache-3 の弧は変わらない" caption="1 台に 1 点のリング。cache-4 は cache-1 が持っていた弧の一部だけを取る" align="center" >}}

cache-4 の点は、cache-2 と cache-1 の間に入りました。cache-2 の点を過ぎてから cache-4 の点までのキーは、以前は cache-1 まで進んでいましたが、今は手前の cache-4 で止まります。それ以外のキーは、時計回りに最初に出会うサーバーが変わらないので動きません。リングのコードは次の通りです。点を並べた配列から、[bisect](https://docs.python.org/3/library/bisect.html) の二分探索で次の点を探します。

```python
from bisect import bisect_left

class Ring:
    def __init__(self, servers, v):
        # 1 台を v 個の点として置く。点の位置は "cache-1#0" のような名前のハッシュ値
        pts = sorted((h(f"{s}#{i}"), s) for s in servers for i in range(v))
        self.pos = [p for p, _ in pts]
        self.owner = [s for _, s in pts]

    def lookup(self, x):
        # x と同じ位置か、それより後ろで最初の点。末尾を越えたら先頭の点に戻る
        return self.owner[bisect_left(self.pos, x) % len(self.pos)]
```

点の位置はサーバーの名前だけで決まるので、どのクライアントでも、サーバーの一覧をどの順に並べても、同じリングになります。台数で割る方法は一覧の何番目かで保存先が決まるので、クライアントごとに一覧の順が違うと、同じキーが別のサーバーに行きます。

### 1 台に 1 点では、受け持つ割合が点の間隔で決まる

リングで動くのは足した 1 台の分だけですが、その量は、新しい点が前の点からどれだけ離れているかで決まります。サーバーが受け持つ範囲も、自分の点と、その手前にある点との間にある弧の長さです。名前のハッシュ値は一様に散るはずでも、3 個や 4 個の点では、間隔が揃いません。

冒頭の図に載せた値は、cache-1 から cache-4 という名前で測った 1 回の値です。名前を変えると点の位置も変わるので、サーバーの名前を変えて同じ実験を 1,000 回繰り返し、4 台目を足した時に動いた割合を求めたのが次の図です。1,000 回の試行ではキーを数えず、弧の長さから割合を計算しています。

{{< figure src="images/consistent-hashing_trials.webp" alt="横軸が 4 台目を足した時に動いたキーの割合、縦軸が 1,000 回のうちの回数のヒストグラム。0〜2.5% が 82 回で最も多く、右へ行くほど減り、88% 近くまで続く。25% に破線、冒頭の図の 38.9% に赤い線" caption="1 台に 1 点のリングで、名前を変えて 4 台目を足した 1,000 回" align="center" >}}

動いた割合は 0.0% から 88.4% まで広がり、[中央値](/ml/math/median/)は 21.3% でした。1,000 回の平均は 25.5% で 1/4 に近くても、1 回ごとの結果は 1/4 から大きく外れます。

0〜2.5% の回は、足したサーバーがほとんどキーを受け取らず、足した容量がほぼ使われない回です。動くキーが少ないことと、足したサーバーがキーを受け持つことは別です。3 台の時点で 1 台が半分より多くを持っていた回は、1,000 回のうち 742 回ありました。3 個の点を円にランダムに置くと、一番長い弧が半周を超える確率は 3/4 なので、この結果は計算とも合います。

#### 1 台が落ちた時

偏りは、サーバーを外した時にも出ます。4 台から cache-2 を外すと、cache-2 のキーは時計回りで次にある点のサーバーに行きます。1 台に 1 点のリングでは、次の点は 1 つなので、全部が 1 台に行きます。

{{< figure src="images/consistent-hashing_fail.webp" alt="cache-2 を外した後に 3 台が受け持つ割合。左の 1 台に 1 点では、cache-2 の 16.6% が全て cache-4 に行き、cache-4 は 55.5%、cache-1 は 9.6%、cache-3 は 34.9%。右の 1 台に 100 点では、cache-2 の分が cache-1 に 9.3%、cache-3 に 4.7%、cache-4 に 10.4% と分かれ、32.9%・30.0%・37.1%" caption="4 台から cache-2 を外した後に受け持つ割合。斜線が cache-2 から引き継いだキー" align="center" >}}

左の cache-4 は、自分の 38.9% に cache-2 の 16.6% を足して 55.5% を持つことになりました。落ちたサーバーの隣が負荷に耐えられずに落ちると、そのキーはさらに次のサーバーに行きます。サーバーの停止をどう検知するかは [Heartbeat](/notes/distributed-systems/heartbeat/) で扱っています。

### 仮想ノードの数

偏りを減らすには、1 台のサーバーをリングの何か所にも置きます。この 1 か所ずつを仮想ノード（virtual node）と呼びます。先ほどの `Ring` の `v` がその数で、`"cache-1#0"` から `"cache-1#99"` のように名前に番号を付けてハッシュ値を求めます。

1 台が受け持つ範囲は短い弧の合計になり、弧の長さのばらつきが平均されます。cache-2 を外した図の右側で、cache-2 のキーが 3 台に分かれたのも、cache-2 の点が 100 か所に散っていて、それぞれの点の次に来る点の担当がばらばらだからです。

10 台のサーバーで名前を変えて 200 回ずつ試し、一番多く持つサーバーが平均の何倍を持つかを数えました。

{{< figure src="images/consistent-hashing_vnodes.webp" alt="横軸が 1 台あたりの点の数（1・4・16・64・256・1024）、縦軸が一番多く受け持つサーバーの割合を平均で割った値。中央値は 2.85・1.84・1.39・1.20・1.09・1.05、95% 点は 4.19・2.52・1.66・1.31・1.16・1.07" caption="10 台で、1 台あたりの点の数ごとの偏り（名前を変えて 200 回）" align="center" >}}

1 台に 1 点では、一番多いサーバーが中央値で平均の 2.85 倍を持ちます。点を 4 倍にするごとに、平均からのずれはおよそ半分になり、64 点で 1.20 倍、256 点で 1.09 倍でした。ずれは点を増やした倍率の平方根に反比例するので、偏りを 1 桁減らすには点が 100 倍必要です。

よく使われる実装が置く点の数は次の通りです（2026 年 11 月時点の公式文書とソースを元にしています）。

| 実装 | 1 台あたりの点 | 備考 |
|---|---|---|
| [libketama](https://github.com/RJ/ketama)（memcached のクライアント） | 160 | MD5 1 回で 4 点を作る |
| nginx の [`hash ... consistent`](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#hash) | 160 | ketama と互換 |
| Envoy の [ring_hash](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/load_balancing_policies/ring_hash/v3/ring_hash.proto) | 全体で 1,024 以上 | 全体の点を台数で分ける |
| Cassandra の [`num_tokens`](https://cassandra.apache.org/doc/latest/cassandra/getting-started/production.html) | 16 | [4.0 で 256 から変更](https://github.com/apache/cassandra/blob/cassandra-4.0/NEWS.txt) |

libketama は、サーバーごとのメモリの量に比例して点の数を変え、大きいサーバーに多くのキーを渡します。

Cassandra は点をトークンと呼びます。16 は少なく見えますが、点の位置を乱数で決めるのではなく、偏りが小さくなるように位置を選ぶ設定と組み合わせる前提です。

### 複製を次の点に置くと、同じサーバーに重なる

データを保存する用途では、1 つのキーを複数のサーバーに複製します。[Amazon Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf) では、キーを担当するサーバーに加えて、リングを時計回りに進んだ次のサーバーにも複製を置きます。仮想ノードを使ったリングでこれをそのまま実装し、時計回りで次に来る 3 点のサーバーを複製の置き場所にすると、次のようになりました。

{{< figure src="images/consistent-hashing_replica.webp" alt="左は 4 台・1 台に 100 点のリングの一部を直線に伸ばした図。user:2 の位置の後ろに、サーバー 1 の点が 3 つ続いていて、次の 3 点を取ると 3 つとも 1 番になる。同じサーバーを飛ばすと 1・4・2 になる。右は、3 つの複製のうち 2 つ以上が同じサーバーに載るキーの割合で、3 台で 73.3%、4 台で 59.0%、6 台で 43.2%、10 台で 27.7%" caption="時計回りで次に来る 3 点に複製を置いた時、同じサーバーに重なるキー" align="center" >}}

`user:2` の後ろにはサーバー 1 の点が 3 つ続いていて、3 つの複製が全て同じサーバーに載りました。3 台のサーバーに 3 つの複製なら、1 台に 1 つずつ載りそうに見えますが、73.3% のキーで 2 つ以上が同じサーバーに重なりました。そのサーバーが落ちると、そのキーの複製は 2 つ同時に失われます。

Dynamo では、同じ物理サーバーの点を飛ばし、異なるサーバーが複製の数だけそろうまでリングを進みます。図の左で下の行が、その取り方です。ライブラリを使わずにリングを自分で書く時に、見落としやすい所です。さらに Dynamo は、複製を複数のデータセンターに分けて置き、データセンター全体が落ちても読めるようにしています。同じラックや電源を共有するサーバーは一緒に止まりやすいので、自分でリングを書く時も、別のサーバーとして数えない方が安全です。

複製を置くと、仮想ノードの数にも別の面が出てきます。点を増やすと 1 台がデータを分け合う相手も増え、どの 2 台が同時に落ちても、どこかの範囲で複製が 2 つ失われやすくなります。Cassandra が[運用の手引き](https://cassandra.apache.org/doc/latest/cassandra/getting-started/production.html)で、点を増やすと可用性が下がると挙げているのはこのためです。複製の食い違いを直す[修復](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)で、個別に扱う範囲の数も増えます。点の数は、偏りだけで決めるものではありません。

<br>

#### 複製の食い違いを直す

複製を置いた後も、サーバーが一時的に落ちている間の書き込みは、複製の間に食い違いを残します。Dynamo は、仮想ノード 1 つが受け持つキーの範囲ごとに [Merkle Tree](/notes/blockchain-systems/merkle-tree/) を持ち、複製どうしでルートのハッシュ値を比べて、違う部分木だけを辿って直します。何台に書けば成功とするか、何台から読むかの決め方は [Quorum](/notes/distributed-systems/quorum/) で扱っています。

### 人気のキーは、点を増やしても分かれない

ここまでは、キーの数を均等に分ける話でした。実際の要求は、一部のキーに集まります。4 台・1 台に 100 点のリングで、要求の数が、人気の順位に反比例する（Zipf 分布、s = 1）として、各サーバーに届く要求を数えました。どのキーが人気かは、ハッシュ値と関係なく決めています。

{{< figure src="images/consistent-hashing_hot.webp" alt="4 台それぞれについて、キーの数と要求の数を割合で並べた棒グラフ。キーの数は 23.5・24.4・25.3・26.7% とほぼ均等だが、要求の数は 17.2・25.4・24.5・33.0% で、cache-4 が多い。1 番人気のキーだけで 8.3% で、それを担当するのが cache-4" caption="4 台・1 台に 100 点で、キーの数と要求の数を割合で比べる" align="center" >}}

キーの数はほぼ 25% ずつなのに、要求は cache-4 に 33.0% 集まりました。1 番人気のキーだけで要求の 8.3% があり、そのキーを担当するのが cache-4 です。1 つのキーは 1 台にしか行かないので、点の数をいくら増やしても、このキーの 8.3% は分かれません。上位 10 個のキーで要求の 24.2% あり、どのサーバーが人気のキーを担当するかで偏りが決まります。

人気のキーには、振り分け方の外で手を打ちます。例えば、アプリケーションの手元にもキャッシュを置く、人気のキーだけ複数台に複製して読む先を分ける、などです。書き込みが 1 つのキーに集まるなら、カウンターを複数のキーに分けて後で合計するように、キーの設計を変えます。キーごとのデータの大きさの偏りも同じで、キーの数を揃えるだけでは消えません。

[Consistent Hashing with Bounded Loads](https://arxiv.org/abs/1608.01350) は、1 台に届く要求が平均の決まった倍数を超えたら、その要求を時計回りで次のサーバーへ回す方法です。HAProxy の [`hash-balance-factor`](https://docs.haproxy.org/2.8/configuration.html#4.2-hash-balance-factor) がこれを実装していて、[Google Research のブログ](https://research.google/blog/consistent-hashing-with-bounded-loads/)によると、Vimeo はこれを使ってキャッシュの帯域を約 8 分の 1 に減らしました。ただし、同じキーが常に同じサーバーへ行く、という性質は一部手放すことになります。

### 他の振り分け方との比較

台数を変えても動くキーが少ない振り分け方は、リングの他にもあります。以下は、同じ 10 万個のキーで、3 台から 4 台に足した時と、4 台から 2 台目の cache-2 を外した時に動いた割合と、4 台での偏りを測った結果です。動く量の最小は、足す時は新しい 1 台が受け持つ割合、外す時は外したサーバーが受け持っていた割合で、均等ならどちらも 25% です。

| 方法 | 足す | 外す | 偏り | 1 回の検索 |
|---|---|---|---|---|
| 台数で割る | 75.0% | 74.9% | 1.01 | 割り算 1 回 |
| リング（1 台に 1 点） | 38.9% | 16.6% | 1.56 | 二分探索 |
| リング（1 台に 100 点） | 26.7% | 24.4% | 1.07 | 二分探索 |
| Jump Consistent Hash | 24.9% | 66.9% | 1.01 | 台数の対数に比例 |
| Rendezvous | 25.0% | 25.1% | 1.00 | 全台を計算 |
| Maglev（表 65,537） | 25.1% | 25.2% | 1.01 | 表を 1 回引く |

偏りは、一番多く受け持つサーバーの割合を平均で割った値です。1 台に 1 点のリングで「外す」が 16.6% なのは、外した cache-2 が受け持っていた割合がそれだけだったからで、少ないほど良いという意味ではありません。

[Jump Consistent Hash](https://arxiv.org/abs/1406.2294) は、Google の Lamping 氏と Veach 氏が 2014 年に発表した方法で、表も点も持たずに数行の計算で 0 から N−1 の番号を返します。足す時は最小の 25% で、偏りもほぼありません。

ただし、外せるのは末尾の番号だけです。2 台目を外して番号を詰めると 66.9% が動きました。番号を順に振る制約があるので、サーバーが任意に落ちるキャッシュより、台数を計画して増やすデータの保存に向く方法です。

<br>

[Rendezvous Hashing](https://en.wikipedia.org/wiki/Rendezvous_hashing) は、キーとサーバー名の 2 つから求めたハッシュ値を全台について計算し、最大のサーバーを選びます。どの台を外しても、そのサーバーを選んでいたキーだけが動きますが、1 回の検索で台数分の計算が必要です。

[Maglev](https://research.google/pubs/maglev-a-fast-and-reliable-software-network-load-balancer/) は Google がロードバランサーについて書いた論文で、サーバーの一覧から大きさ 65,537 の表を作り、キーは表を 1 回引くだけで保存先が決まります。Envoy の [maglev](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/load_balancing_policies/maglev/v3/maglev.proto) も既定の表は 65,537 です。

[Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/) は、どれとも違い、キーを 16,384 個のスロットに分け、どのスロットをどのノードが持つかを表で管理します。ノードを足す時は、どのスロットを移すかを指定して移します。動く量をハッシュの計算で決めるのではなく、表を書き換えて決める方法です。

<br>

#### 全てのクライアントで同じハッシュ関数を使う

どの方法でも、保存先を決めるクライアントが複数あるなら、全てが同じハッシュ関数で同じ値を出す必要があります。サーバーの一覧と点の置き方も全てのクライアントで揃える必要があり、それを配る仕組みは別に用意します。Python の組み込みの `hash()` は、文字列のハッシュ値に[プロセスごとに違う乱数を混ぜる](https://docs.python.org/3/reference/datamodel.html#object.__hash__)ので、保存先の計算に使うと、プロセスごとに結果が変わります。

```python
import subprocess, sys

for seed in ["1", "2", "3"]:
    out = subprocess.run([sys.executable, "-c", "print(hash('user:42') % 4)"],
                         capture_output=True, text=True, env={"PYTHONHASHSEED": seed}).stdout
    print(f"PYTHONHASHSEED={seed}: user:42 -> サーバー {out.strip()}")
```

```text
PYTHONHASHSEED=1: user:42 -> サーバー 1
PYTHONHASHSEED=2: user:42 -> サーバー 2
PYTHONHASHSEED=3: user:42 -> サーバー 2
```

同じキーが、プロセスによって 1 番と 2 番のサーバーに行きました。libketama が MD5 を使うのは、言語や実装が違うクライアントでも同じ位置を求められるからです。暗号の用途なら MD5 ではなく [SHA-256](/notes/security/sha-256/) などを選びますが、ここで必要なのは衝突への強さではなく、どこで計算しても同じ値になることです。

### 設定を見る順番

これから Consistent Hashing を使う人も、既存のシステムで出会った人も、冒頭の図で 3 段のどれに近いかを見ることから始まります。

最初に、キーが動いた時に何が起きるかを決めます。キャッシュなら外れて DB へ読みに行くだけで、動く量は、増設した直後に DB の負荷として現れます。データを保存するサーバーなら、動いた分のコピーが必要です。

次に、1 台に何点置いているかを見ます。libketama や nginx の 160 点なら、冒頭の図で 3 段目に近く、10 台で測った値では、一番多いサーバーでも平均の 1〜2 割増しです。自分でリングを書いて 1 台に 1 点しか置いていなければ、2 段目と同じことが起きます。サーバーの大きさが違うなら、点の数をそれに比例させます。

複製を置くなら、同じ物理サーバーの点を飛ばしているかを見ます。飛ばしていなければ、3 台に 3 つの複製を置いても、7 割のキーで 2 つ以上が同じサーバーに載ります。

最後に、偏りが残るなら、キーの数ではなく要求の数を見ます。サーバーごとのキーの数が揃っていて要求だけが偏っているなら、点を増やしても直りません。人気のキーを手元のキャッシュや複製で分けるか、Bounded Loads のように上限を決めます。

Consistent Hashing が決めるのは保存先だけで、移している間の書き込みの反映や、要求の向き先の切り替えは別の手順です。キーの範囲で検索する用途では、ハッシュ値で並びが崩れるので、[Partitioning](/notes/database-systems/partitioning/) の範囲（Range）のように、キーの範囲で分ける方が向きます。台数がほとんど変わらないなら、台数で割る方法で足ります。
