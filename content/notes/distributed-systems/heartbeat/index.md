ハートビート（heartbeat）は、ノードが一定の間隔で送る「動いている」という短い信号です。受け取る側（以下、monitor）は、一定時間（タイムアウト）届かなければ、そのノードが落ちたと判定します。Kubernetes のノード、[etcd](https://etcd.io/) のリーダー、[Apache Cassandra](https://cassandra.apache.org/) のノードは、どれもこの仕組みで監視されています。仕組みが単純なので、次の前提を置いたまま実装や設定をしがちです。

- ハートビートが途絶えたら、送る側が止まっている
- ハートビートが届いていれば、送る側は仕事をしている
- タイムアウトは短いほど、早く正しく気づける
- 落ちたと判定したノードは、もう何もしない

4 つとも、成り立たない場合があります。以下は、ハートビートを送る 2 台を一度も止めず、monitor だけを 1.5 秒止めた時の実測です。

{{< figure src="images/heartbeat_monitor_pause.webp" alt="動く図。node-a と node-b は 100 ms ごとにハートビートを送り続ける。2 秒から 3.5 秒まで monitor が止まり、その間に届いたハートビートは受信バッファに溜まって 31 通になる。再開した直後、monitor は 2 台とも落ちたと判定し、1 ms も経たないうちにバッファの 31 通（node-a 16 通、node-b 15 通）をまとめて読んで生き返ったと判定し直す" caption="monitor だけを 1.5 秒止めた時の送信・受信・判定（実測した時刻を 0.5 倍速で再生）" align="center" >}}

再開した直後、monitor は動いている 2 台を両方とも落ちたと判定しました。止まっていたのは monitor の方で、2 台が送ったハートビートは、読まれないまま受信バッファに届いていました。受信バッファは、プロセスがまだ読んでいない UDP のパケットを OS が溜めておく場所です。

この monitor は、ハートビートを受け取る処理と、落ちたかどうかを判定する処理を別々のスレッドで動かしています。再開した時に判定のスレッドが先に動いたので、溜まっていたハートビートを読む前に判定が出ました。

クラスタを運用していると、「ノードが落ちた」というログやアラートを見て確認しに行くと、そのノードは何事もなく動いている、ということがあります。逆に、監視の画面では全て緑なのに、利用者からは応答が無いと言われることもあります。どちらも、ハートビートが何を測っているかを取り違えると起きます。

<br>

本記事では、ハートビートでノードを監視する人と、これから自分で実装する人に向けて、上の 4 つの前提が崩れる場面を実験と実例で順に示します。

実験は Linux 上の Python 3.14 で、全て 127.0.0.1 の UDP で行いました。

### 途絶えた時に分かること

monitor に分かるのは、「最後にハートビートを受け取ってから、どれだけ経ったか」だけです。送る側が止まったのか、遅れているだけなのかは、その観測からは区別できません。以下は、同じ「届かない」という観測を生む原因です。

| 原因 | 送る側は動いているか |
|---|---|
| プロセスやマシンが落ちた | 動いていない |
| 送る側が GC（Garbage Collection）などで一時的に止まった | 再開すれば動く |
| ネットワークが落とした・遅らせた | 動いている |
| monitor が止まっていて読めなかった | 動いている |

この区別が原理的にできないことは、[FLP Impossibility](../flp-impossibility/) で、タイムアウトの満了は故障の証明ではなく疑いである、という形で扱っています。そのため、判定を「落ちた」ではなく「疑わしい」として扱い、後で取り消せる形にした仕組みもあります。

例えば、メンバーの死活をノード同士で調べ合う [SWIM](https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf) は、応答の無いノードをすぐには落ちたとせず、まずランダムに選んだ数台に、代わりに問い合わせてもらいます。それも失敗したら Suspect（疑わしい）という状態にし、猶予の時間が過ぎてから落ちたと確定します。

SWIM では各ノードが incarnation number という番号を持ち、Suspect にされたノードは、この番号を増やした生存の通知を広めて疑いを打ち消せます。

Suspect の間は、リーダーの選び直しやデータの移動を始めません。ノードが実は動いていた時に、無駄な負荷だけが残るからです。猶予が過ぎて落ちたと確定した後は、番号を増やした通知でも取り消せず、そのノードはグループへの参加からやり直します。

表の最後に挙げた原因は、送る側をいくら丈夫にしても防げません。冒頭の図は、この原因を再現したものです。

### monitor が止まった時

実験の monitor は、最後にハートビートを受け取った時刻をノードごとに持ち、50 ms ごとに「500 ms 以上届いていないノード」を落ちたと判定します。時刻は、壁時計ではなく、単調増加して後戻りしないモノトニッククロック（monotonic clock）の `time.monotonic()` で測ります。

壁時計は、時刻をネットワーク越しに合わせる [NTP](https://www.rfc-editor.org/rfc/rfc5905)（Network Time Protocol）の補正や手動の変更で前後に跳ぶので、経過時間の計算に使うと、時計がタイムアウトより大きく進んだだけで、全てのノードが落ちたと判定されます。

ハートビートを受け取る処理と、判定する処理をスレッドで分けた作り（以下、thread）は、次のとおりです。全体は [monitor_pause.py](https://github.com/nao1215/debimate/blob/main/content/notes/distributed-systems/heartbeat/lab/monitor_pause.py) にあります。

```python
INTERVAL = 0.100   # ハートビートの間隔
TIMEOUT = 0.500    # これだけ届かなければ落ちたと判定する
TICK = 0.050       # 判定の周期

def receiver():                 # 受信のスレッド
    while True:
        data, _ = sock.recvfrom(64)
        on_heartbeat(data)      # last[node] = time.monotonic()

def judge():                    # 判定のスレッドが TICK ごとに呼ぶ
    now = time.monotonic()
    for node, seen in last.items():
        if node not in dead and now - seen > TIMEOUT:
            dead.add(node)
            log("dead", node=node)
```

開始から 2 秒後に、実験の親プロセスが monitor に SIGSTOP を送り、1.5 秒後に SIGCONT で再開させます。SIGSTOP はプロセスにある全てのスレッドを止めるので、GC の停止や、VM が一時停止された時と同じく、monitor から見た時間だけが飛びます。送る側の node-a と node-b は止めません。

<br>

#### 作りによって結果が変わる

monitor の作りを 4 通りに変えて、20 回ずつ試した結果です（[monitor_pause_output.txt](https://github.com/nao1215/debimate/blob/main/content/notes/distributed-systems/heartbeat/lab/monitor_pause_output.txt)）。

| monitor の作り | 落ちたと判定した試行 |
|---|---|
| thread: 受信と判定を別のスレッドで行う | 8/20 |
| loop1: 1 つのループで 1 通読んで判定 | 20/20 |
| drain: 1 つのループで全部読んで判定 | 0/20 |
| guard: thread に、判定を待つ処理を足す | 0/20 |

guard が判定を待つのは、自分が止まっていたと気付いた時です。

thread で落ちたと判定したのは、20 回中 8 回でした。再開した直後は、受信と判定の 2 つのスレッドが、どちらも動ける状態になり、どちらが先に動くかで結果が変わります。

判定のスレッドが先に動くと、最後に受け取ったのは 1.5 秒前なので、2 台とも落ちたと判定します。1 ms も経たないうちに受信のスレッドがバッファの 31 通を読み、2 台とも生き返ったと判定し直します。冒頭の図は、この順で動いた試行です。

loop1 は 20 回全てで落ちたと判定しました。再開した後に読むのは、バッファで先頭にある 1 通だけです。その直後の判定では、もう 1 台から最後に受け取ったのはまだ 1.5 秒前のままです。

<br>

#### 判定を見送る

直し方は 2 つあります。drain は、届いている分を全て読んでから判定するので、バッファに溜まっていたハートビートが判定より先に反映されます。ただし、受信と判定を 1 つのループで回す作りの時にしか使えません。

guard は、判定の間隔そのものを測ります。50 ms ごとに動くはずの判定が 200 ms 以上空いたら、自分が止まっていたとみなし、それからタイムアウトの長さ（500 ms）だけ判定を見送ります。

```python
now = time.monotonic()
if now - prev > GUARD_GAP:      # GUARD_GAP = 4 * TICK = 200 ms
    log("skip", gap_ms=round((now - prev) * 1000))
    hold_until = now + TIMEOUT
prev = now
if now < hold_until:
    continue                    # この周期は判定しない
judge()
```

実験の 20 回では、どれも 1.5 秒ほどの空きを見つけて判定を見送り、その間に受信のスレッドが溜まっていた 30〜31 通を読み終えていました。

Cassandra の故障検知（[FailureDetector.java](https://github.com/apache/cassandra/blob/cassandra-5.0.6/src/java/org/apache/cassandra/gms/FailureDetector.java)、5.0.6 で確認）にも、同じ考え方の処理があります。判定の間隔が既定で 5 秒（`cassandra.max_local_pause_in_ms`）を超えたら `Not marking nodes down due to local pause` というログを出し、そこから同じ長さの間、どのノードも落ちたと判定しません。

monitor 自身が止まる原因は、GC、CPU の割り当ての上限、ディスクの書き込み待ち、VM の一時停止など、送る側が止まる原因と同じです。送る側の停止にだけ備えて、monitor の停止を考えない作りは、冒頭の図のように、動いているノードを落ちたと判定します。

特に、1 台の monitor が全てのノードを見る構成では、monitor の停止や過負荷は、全てのノードが一斉に落ちたという判定として現れます。monitor が落ちたままなら、今度はどのノードの故障も見つけられません。

### 届いているのに答えない時

前の節は、送る側が動いているのに落ちたと判定される話でした。逆に、送る側が仕事をしていないのに、ハートビートだけは届き続けることもあります。

実験の node は、要求を処理するループと、100 ms ごとにハートビートを送る処理を持ちます。開始から 2 秒後に、処理のループがデッドロックします。別のスレッドが 2 つのロックを処理のループとは逆の順に取り、互いに相手のロックを待ち続けるようにしました。

client は 100 ms ごとに要求を送り、300 ms 以内に応答が無ければ失敗として記録します。応答を待つ間は次の要求を送らないので、デッドロックの後は失敗が約 0.3 秒おきに並びます。ハートビートは、別のスレッドから送る場合と、処理のループで送る場合の 2 通りで比べました。

{{< figure src="images/heartbeat_gray_failure.webp" alt="上の段はハートビートを別のスレッドから送る場合で、2.0 秒に処理のループがデッドロックした後も、ハートビートは 5 秒まで 100 ms ごとに届き続けるが、要求は全て返らない。monitor は一度も落ちたと判定しない。下の段は処理のループから送る場合で、デッドロックの後はハートビートが届かなくなり、2.43 秒に落ちたと判定する。要求は上の段と同じく全て返らない" caption="ハートビートを送る場所ごとの、ハートビートと要求の結果" align="center" >}}

実験の出力は次のとおりです。出力の thread は別のスレッドから送る場合、inloop は処理のループから送る場合で、前の節で比べた monitor の作りとは関係ありません。デッドロックの直前に送った分を数えないよう、ハートビートは 1 間隔分の 0.1 秒、要求は応答を待つ 300 ms より長い 0.5 秒だけ、2.0 秒からずらして数えました。

```text
thread  2.1 秒以降のハートビート  29  2.5 秒以降の成功 0  タイムアウト 10  落ちたと判定した時刻 []
inloop  2.1 秒以降のハートビート   0  2.5 秒以降の成功 0  タイムアウト 10  落ちたと判定した時刻 [2.431]
```

別のスレッドから送ると、2.1 秒以降もハートビートは 29 通届き、monitor は 5 秒の間、一度も落ちたと判定しませんでした。要求は 2 秒以降、1 つも返っていません。ハートビートを送るスレッドが測っていたのは、そのスレッドが動いていることだけでした。

処理のループで送ると、ループが止まった時にハートビートも止まり、monitor は 2.43 秒に落ちたと判定しました。最後のハートビートは 1.93 秒で、そこからタイムアウトの 500 ms 後です。代わりに、ループが他の仕事で遅れるとハートビートも遅れます。デッドロックの前でも、ハートビートの間隔は 100 ms から最大 200 ms まで揺れていました。

TCP の接続が切れたかどうかで代わりにできないのも、同じ理由です。[TCP](https://www.rfc-editor.org/rfc/rfc9293) の接続は、プロセスが[デッドロック](/notes/database-systems/deadlock/)や GC で応答しなくなっても開いたままです。経路上のファイアウォールがパケットを黙って捨てると、送る側は接続が切れたことに長い間気付けません。

<br>

#### グレー障害

監視する側からは正常に見え、利用する側からは異常に見える状態は、2017 年の[論文](https://dl.acm.org/doi/10.1145/3102980.3103005)で gray failure と名付けられました。

AWS のホワイトペーパーは、日本語版で[グレー障害](https://docs.aws.amazon.com/ja_jp/whitepapers/latest/advanced-multi-az-resilience-patterns/gray-failures.html)と訳しています。論文は、監視と利用者で観測が食い違うこと（differential observability）として定義しています。上に示した図では、上の段がその小さな例です。

ハートビートは届くことしか見ないので、ディスクが壊れていても、ハートビートさえ届けば健全と判定されます。ブロックチェーンの[インデクサー](../../blockchain-systems/indexer/#上限を超えた時の-4-つの型)でも、取り込みが止まったまま、準備ができたかを示す応答だけが正常を返し続ける例があります。誤った値を返すノード（[ビザンチン障害](../byzantine-fault-tolerance/)）も、ハートビートでは見つけられません。

ハートビートを処理のループから送れば、利用者の要求と同じ所が止まった時に気付けます。Kubernetes の [liveness probe](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/) のように、monitor から実際の処理を通る要求を送る方法もあります。どちらの方法でも、ハートビートが届いた時に何が動いていると言えるのかを先に決めておきます。

ただし、liveness probe を送る kubelet（各ノードで動く Kubernetes のエージェント）は、そのノードの上で動いています。ノード自体が落ちた時は、次の節で扱う Lease の更新が止まることで見つけます。

### 間隔とタイムアウトの決め方

タイムアウトを短くすれば、本当に落ちたノードに早く気づけます。その代わり、送る側や monitor の短い停止、ネットワークの揺れで誤検知します。逆に、タイムアウトを伸ばすと、はじめは誤検知が大きく減ります。ただし、数秒の停止が混じる環境では、停止より短いタイムアウトはどれも誤検知するので、ある所から先は減り方が鈍ります。どこで鈍るかは、遅延のばらつきと停止の長さで変わります。実際のソフトウェアでは、既定値が桁で違うほど離れています。

| ソフトウェア | 送る間隔 | 落ちたと判定するまで |
|---|---|---|
| etcd（v3.6） | 100 ms | 1,000 ms |
| Kubernetes のノード（v1.37） | 10 秒 | 50 秒 |
| Apache Pekko のクラスタ（v1.7.1） | 1 秒 | φ が 8 を超えた時 |
| Cassandra（5.0.6） | 1 秒ごとの gossip | φ が 8 を超えた時 |

φ は、Pekko と Cassandra が使う判定の値で、この節の後半で説明します。Cassandra の gossip は、各ノードが 1 秒ごとに数台を選び、自分が持つハートビートの記録を交換して、伝言のようにクラスタ全体へ広める方式です。

ノードが n 台の時、1 台の monitor が全てを見るなら 1 周期に届くハートビートは n 本ですが、全てのノードが互いに送り合うと n×(n−1) 本に増えます。gossip は 1 ノードが送る相手を数台に絞るので、1 ノードが送る本数はノード数に依存しません。ただし、1 通に載せる記録はノード数とともに増えます。

{{< figure src="images/heartbeat_topology.webp" alt="ノードが 5 台の時に 1 周期に流れるハートビートの本数を 3 つの形で比べた図。左は 1 台の monitor に 5 台から 1 本ずつ届き 5 本。中央は全ての組が両向きに送り合い、n×(n−1) = 20 本。右の gossip は各ノードが 1 台だけに送る例で 5 本だが、各ノードが 5 台分の記録を持ち、1 通にそれを載せる" caption="ノードが 5 台の時の、監視の形ごとのハートビートの本数" align="center" >}}

etcd が使う Raft では、リーダーがフォロワーへ書き込みを複製する通信がハートビートを兼ねます。etcd の値は[公式の手引き](https://etcd.io/docs/v3.6/tuning/)にあり、`--election-timeout` はメンバー間の往復時間を基準に決めるように書かれています。リーダーが落ちたと判定した後に起きるのは、[Leader and Followers](../leader-and-followers/) で扱っている次のリーダーを選ぶ選挙で、次に挙げる Kubernetes の後始末に比べれば軽い処理です。ただし、誤検知で選挙が続けて起きると、選び直している間は書き込みが進みません。

Kubernetes では、kubelet がノードごとの [Lease](https://kubernetes.io/docs/concepts/architecture/leases/) を 10 秒ごとに更新し、それがハートビートになります。kube-controller-manager は、[`--node-monitor-grace-period`](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-controller-manager/) が既定で 50 秒で、10 秒ごとの更新が 5 回分届かなければ、ノードを異常とします。

判定の後には、そのノードで動く Pod（コンテナをまとめた実行の単位）を他のノードへ移す処理が控えています。誤検知した時の後始末が重いほど、タイムアウトは長くなります。

#### φ accrual failure detector

表の Pekko と Cassandra は、決まった時間ではなく、φ（ファイ）という値で判定します。林原尚浩氏らが 2004 年に提案した [φ accrual failure detector](https://dspace.jaist.ac.jp/dspace/handle/10119/4784) は、これまでに届いたハートビートの間隔から分布を求め、「これだけ長い沈黙が、動いているノードで起きる確率」を計算し、φ = −log10（その確率）とします。

φ が 8 なら、動いているノードでその沈黙が起きる確率は 10⁻⁸ です。φ が 1 増えるたびに確率は 1/10 になり、φ = 1 は 10%、φ = 3 は 0.1% です。この確率は、仮定した分布が実際の間隔と一致する時の値で、現実に誤検知する確率そのものではありません。

確率をどの分布で求めるかは実装ごとに違います。[Akka](https://doc.akka.io/libraries/akka-core/current/typed/failure-detector.html) から分かれた [Apache Pekko](https://pekko.apache.org/) の[実装](https://github.com/apache/pekko/blob/v1.7.1/remote/src/main/scala/org/apache/pekko/remote/PhiAccrualFailureDetector.scala)は正規分布を使い、平均に `acceptable-heartbeat-pause`（既定 3 秒）を足します。

Cassandra は指数分布を使い、[CASSANDRA-2597](https://issues.apache.org/jira/browse/CASSANDRA-2597) で計算を簡単にして、「沈黙の長さ ÷ 間隔の平均」に 1/ln 10 を掛けた値を φ にしています。以下は、2 つの式から、既定の閾値 8 で落ちたと判定するまでの沈黙の長さを計算した図です。

{{< figure src="images/heartbeat_phi.webp" alt="横軸は最後のハートビートからの経過時間、縦軸は φ。Pekko は間隔の平均を 1 秒とし、猶予の 3 秒を足すので 4 秒近くまで φ がほぼ 0 のまま進み、標準偏差が 0.1 秒なら 4.5 秒、1 秒なら 9.2 秒で閾値 8 を超える。Cassandra は間隔の平均を 1 秒とすると、φ が経過時間に比例して増え、18.4 秒で 8 を超える" caption="既定の閾値 8 で、落ちたと判定するまでの沈黙の長さ（式から計算）" align="center" >}}

Pekko は、間隔の平均が 1 秒で揃っていれば 4.5 秒、[標準偏差](/ml/math/stddev/)が 1 秒に広がれば 9.2 秒待ちます。揃っている時の標準偏差には、下限の `min-std-deviation`（既定 100 ms）が使われます。

ネットワークが揺れ始めると、自動で待つ時間が伸びるので、誤検知が増えにくい代わりに、本当に落ちた時に気づくのも遅れます。ただし、分布は過去の間隔から求めるので、揺れ始めた直後は待つ時間が伸び切っておらず、誤検知しえます。Cassandra は分布の形を見ず、平均した間隔の約 18.4 倍（8 × ln 10）待ちます。

図は間隔の平均を 1 秒とした場合で、gossip でハートビートを他のノード経由で受け取る Cassandra では、実際の間隔はクラスタの大きさや構成で変わります。

同じ「φ = 8」でも、待つ時間は 4.5 秒から 18 秒まで開きます。φ は確率の形をしていますが、どの分布を仮定したかで意味が変わるので、閾値の数字だけを他のソフトウェアと比べても意味がありません。

### 落ちたと判定したノードが戻ってきた時

冒頭の実験で、monitor は 1 ms も経たないうちに判定を取り消しました。しかし、判定に続く処理は取り消せません。リーダーが落ちたと判定されれば次のリーダーが選ばれ、ノードが異常とされれば Pod が他のノードで起動します。

落ちたと判定されたノード自身は、そのことを知りません。GC で止まっていた古いリーダーが再開すると、自分がまだリーダーだと思ったまま書き込みを受け付け続けます。過半数の応答で書き込みを確定する Raft のような構成では、その書き込みは確定しません。しかし、確定を求めない構成や、外部のストレージに直接書く構成では、2 台が同時にリーダーとして振る舞うスプリットブレインになります。ハートビートの判定だけでは、これを防げません。

<br>

#### 43 秒の途絶と 24 時間の劣化

誤った判定の後始末は、途絶えていた時間よりずっと長く掛かることがあります。2018 年 10 月 21 日、GitHub では機器の交換作業で、米国東海岸のネットワーク拠点と主なデータセンターをつなぐ通信が 43 秒途切れました。[事後の報告](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/)によると、その間に、[MySQL](https://www.mysql.com/) で primary が故障したと判定して切り替える [Orchestrator](https://github.com/openark/orchestrator) が、書き込み先を西海岸のデータセンターに移し始めました。primary は、書き込みを受け付けるリーダーのことです。

[故障検知を説明した文書](https://github.com/openark/orchestrator/blob/master/docs/failure-detection.md)によると、Orchestrator は primary に接続できず、その primary から複製を受けている replica も全て primary に届かない時に、故障と判定します。届かないことを故障とみなす点は、ハートビートと同じです。

東海岸の primary は動いていたので、通信が戻った時には、東西の両方に相手の持たない書き込みが残っていました。サービスの劣化は 24 時間 11 分続き、再発防止策の 1 つは、地域をまたいで primary を昇格させない設定です。

<br>

#### 古いリーダーの書き込みを止める

[過半数](../quorum/)の票でリーダーを選ぶ構成では、分断された少数派にはリーダーが立ちません。それでも、古いリーダーは交代に気付くまで動き続けます。書き込みの確定にも過半数の応答を求める構成なら、古いリーダーは書き込みを確定できません。ただし、新しいリーダーが確定した書き込みを知らないので、古い値を読み取りに返すことがあります。

[Raft](https://raft.github.io/) の[論文](https://raft.github.io/raft.pdf)は 8 節で、リーダーが読み取りに答える前に過半数とハートビートを交換し、自分がまだリーダーかを確認する方法を示しています。同じ節は、過半数から応答を得てから一定時間は新しいリーダーが立たないとみなし、確認を省いて答える方法も挙げています。この方法は、ノード間で時計の進む速さのずれに上限があることを前提にします。

防ぐには、書き込みを受け取る側で古いノードを拒否する仕組みが必要です。[Lease](../lease/) では、期限付きで権利を貸し、権利を貸すたびに増える番号（fencing token）を書き込みに添えさせて、古い番号を拒否する実験をしています。Raft では、リーダーが持つ任期の番号が同じ役割をします。

### ハートビートを監視に使う前に確認すること

「ノードが落ちた」というアラートを見た人も、これからハートビートを実装する人も、確認することは 4 つです。アラートから入る時は、見えたことから次の表で探します。

| 見えたこと | 最初に疑う所 |
|---|---|
| 全てのノードが同時に落ちたと判定された | monitor の停止 |
| 監視は正常なのに、要求が返らない | ハートビートを送る場所 |
| 落ちた判定が出たり消えたりする | タイムアウトの長さ |
| 判定の後に、古いノードが書き込んだ | 書き込みを拒否する仕組み |

monitor が止まった時に、判定を見送れるかを確認します。判定の前に届いている分を全て読むか、判定の間隔が空いたことを見つけて判定を止めます。受信と判定をスレッドで分けた素直な作り（thread）でも、monitor が 1.5 秒止まっただけで、動いている 2 台を落ちたと判定します。

全てのノードが同時に落ちたと判定された時は、まず monitor が動いていたマシンで、GC や CPU の上限、VM の停止が起きていないかをログで見ます。

ハートビートがどの処理から送られているかを確認します。別のスレッドや別のプロセスから送っていれば、そのハートビートが表すのは、そのスレッドが動いていることだけです。要求に答えられるかを知りたいなら、処理の経路から送るか、monitor から実際の要求を送ります。

タイムアウトは、判定の後に動く処理の重さで決めます。選挙のように軽い処理なら短くできますが、往復時間に近づけるほど選挙が続いて書き込みが止まります。Pod の移動のように重い処理なら長くします。φ accrual failure detector を使う時は、閾値の 8 が何秒の沈黙に当たるか、実装の式と実際の間隔から計算しておきます。φ は連続した値なので、警告は φ = 5、切り離しは φ = 8 のように、同じ検知器の上で用途ごとに閾値を変えることもできます。

最後に、落ちたと判定したノードが戻ってきても、古い権利で書き込めないようにします。ハートビートが出せるのは疑いだけで、書き込みを止めるのは fencing token や任期の番号です。

実験のコード・出力・試行ごとの時刻は [lab/](https://github.com/nao1215/debimate/tree/main/content/notes/distributed-systems/heartbeat/lab) にあります。
